## 0. 全局字体（2026-10-24）

- 字体文件：`assets/fonts/sanji_pomo.ttf`（用户提供的「三极泼墨体」，原文件直接使用）。
- 应用方式：`project.godot` 的 `[gui] theme/custom` 指向 `assets/ui/game_theme.tres`：
  - 主题默认字体 = 三极泼墨体（标题 / 按钮 / 短标签）；
  - `TooltipLabel` 字体 = 系统无衬线（Microsoft YaHei 等）—— 所有物品 / 属性 tooltip 自动可读。
- **长说明文字分区**：指引正文、物品详情、配方效果、功法说明、域 / 塔 / 记忆描述、修为说明、
  锻造提示、局内背包提示等统一走 `UIKit.readable_label / readable_note / make_readable()`，
  使用系统无衬线；短标签保持毛笔体。
- 字号仍由 `ui_kit.gd` 的 `F_TITLE / F_SECTION / F_BODY / F_SMALL / F_BADGE` 控制。
- 换字体：覆盖同名 ttf，或改主题 / `UIKit.readable_font()`；首次导入前 editor 可能报
  `No loader found for resource`，再跑一次 `--headless --editor --quit` 完成导入即可。
- ⚠ 不要给单个面板单独换字体：长文本统一走 `UIKit` 的 readable 接口，短文本继续用默认主题字体。

### 三张 Boss 地图：单张 TextureRect 平铺（2026-10-22 第三轮更新）

三张图都是**可平铺的地面纹理**（沙地 / 石板 / 冰砖）。战场地面整个只有 **1 个 TextureRect**：

- **平铺方式**：`texture_repeat = REPEAT_ENABLED` + `stretch_mode = STRETCH_TILE`
  —— TextureRect 拉到多大，纹理就自动铺满多大；改战场大小只改 ArtDB 的 `map_tiles`
- **战场尺寸**：`map_tiles = 6` × `tile_width = 600` → **3600×2028**（旧 3×3 = 1800×1013 的两倍）
  - `tile_width` 定 600 的依据：战斗角色视觉尺寸 45×67.5，地砖内部石纹约 63px ≈ 一个身位
- **无缝做法**：先把原图缩到 600 宽、拼成 **2×2 镜像块**（右上左右翻、左下上下翻、右下双翻），
  再让镜像块去 repeat —— 接缝两侧取同一像素列/行，数学上必然对齐。
  直接 repeat 原图会有淡色接缝（实测左右边差 8~16、上下差 7~16）
- **贴图 shader**：条目里填 `"shader"` 会给这个形象挂 ShaderMaterial（参数走 `shader_params`，
  值为图片路径时自动当贴图 uniform）。主城地面就用它做了「星点流动」，详见 `docs/地面星点流动.md`
- **明暗 / 偏色**：ArtDB 条目的 `"tint"`（默认白 = 原色），乘在 TextureRect 的 `modulate` 上。
  ⚠ 别改原图：冰砖那张原本接近纯白（截取地面区域平均亮度 217），
  `tint = (0.76, 0.80, 0.86)` 后降到 175，角色/界面元素才看得清
- **实现**：`combat_arena._setup_ground_bg()`；未配 `map_tiles` 或贴图缺失 → 回退单张 `SkinVisual`
- **内存**：原图 2730×1536（≈16 MB）用 `CACHE_MODE_IGNORE` 烘完即释放；镜像块缓存只留当前一张
- **边界**：`Camera2D.limit` + 四面隐形墙（墙在第 6 层 = 32，玩家 mask 42），墙内缩 40

## 4. 踩坑（下次导素材先看这几条）

1. **E 盘的「.png」有一半是 JPEG**（文件头 `ffd8ff`）：地图 4 张 + 两张选择界面背景。
   Godot 按扩展名当 PNG 加载会直接失败 → 必须先用 PIL 转真 PNG（脚本 `output/import_art.py`）。
2. **面板框/按钮图有大片透明留白**：直接 9-patch 会连留白一起拉伸。已生成 `*_9p.png`（裁 alpha bbox，按钮再压到高 48）。
3. **不要用「加大 PANEL_MARGIN」避让金框云纹**：锻造台铁砧区是绝对定位，内边距一改「分解装备」按钮就被裁出面板。
   正确做法是缩小 9-patch 边距（`FRAME_PATCH_MARGIN`）。
4. 界面背景要压暗（`modulate.a = 0.32`），否则正文读不清。

## 14. 锻造舞台的 AI 图生图通路（2026-10-25 试点，用户采纳方案 B）

把第 13 节那张 PIL 舞台换成图像生成模型重绘的版本。这一节记的是**通路和限制**，不是一张具体的图。

- **工具**：Qoder 内置 `ImageGen`（早先报 `invalid_model_error`，10-25 已可用）。可选尺寸含 `1024x1024`、`1792x1024` 等。
- **限制一：文生图不吃风格否定词**。提示里写 `matte hand-painted wuxia ink illustration … NOT glossy 3D, NOT photorealistic`，
  仍然出一张写实铁匠铺。**否定式风格约束等于没写**。
- **限制二：孤立看图会误判**。试点 A 单看挺好看，合成到真实 UI 上（PIL 把图铺进 1280×720 再叠现有纸签 / 铜牌）才知道撞得多厉害。
  **美术试点必须先看「叠上现有控件之后」的效果，不能只看生成的那张图。**
- **通路：图生图 + 现有资产当参考图**。`images=["assets/ui/forge/stage_night.png"]` 把 PIL 版当参考喂进去，一次锁住两件事：
  1. **媒介**（出来的还是手绘，不会再滑回写实）；
  2. **构图**（铁砧、炉膛、歇锤点的大位置基本不动）。
  所以 `forge_panel.gd` 里那一整排绝对定位常量（`ANVIL_HIT` / `FURNACE_RECT` / `HAMMER_HOME` / `EQUIP_CENTER` / `PLAQUE_POS` / `DISH_POS` …）
  **一个都不用改**。这是这条通路最大的价值：换美术不换交互落点。
- **尺寸必须回到 1792×1008**。模型只给 1792×1024，而面板按「舞台像素 ÷ 1.4 = 屏幕像素」摆落点；
  1024 高会把比例变成 1.4222，落点整体往下漂。**上下各裁 8 像素**，规则重新成立（脚本里是 `crop_to_ratio()`，宽度不对直接报错）。
- **模型出的图总是偏亮**：实测平均亮度 27.0，而工程里现用的舞台是 20.1。直接接进去，纸签和铜牌会被衬得发灰，
  整个界面从「夜里一炉火」变成「白天一间屋」。**调色不是美化，是把亮度拉回与 UI 同一档。**
- **调色脚本**：`tools/grade_forge_stage.py`，三步缺一不可：
  1. `GAMMA = 1.30` + `COOL_TINT = (0.90, 0.93, 1.03)`：整体沉下去，石头从暖灰变夜灰；
  2. `WARM_RESCUE = 0.42` **只回拉暖色像素**（判据 `R > B + 0.06` 且 `G > B×0.75`，即橙黄族）：
     炉口和它洒在石面上的光是画面里唯一的饱和色，压暗时不能一起干掉，否则炉火变余烬、镜头就没有落点；
  3. `VIGNETTE = 0.20` 暗角（`hypot(nx×0.85, ny) - 0.45` 的 1.6 次方）：把注意力钉在砧面，
     同时把顶部与右侧（本来就会被顶栏和兵器架盖住）压成低信息量。
  - **安全闸**：`LUM_RANGE = (18.0, 22.0)`，出区间直接 `SystemExit` 不写文件——改参数而不是硬塞一张过亮的图。
  - 结果：脚本在写盘前报 **19.9**；存成 uint8 PNG 后按同一公式复核是 **19.7**（量化掉的那 0.2 属正常，不要为了对齐数字反复重存）。
    对照：AI 原片 27.0（1792×1024）、被替换的 PIL 版 20.1（1792×1008）—— 复核亮度时这两个数就是上下参照。
- **`assets/` 整个目录没进版本库**，覆盖就找不回来。脚本因此在写文件前把旧图整份备份成 `stage_night.png.bak_pil`（当前是 PIL 版）。
  换图前确认这个备份存在，比确认 git 干净更管用。
- **AI 原片留档**：`vibe_images/forge_stage_pilot_b_1792933829447_273eb5ae.png` 是 `grade_forge_stage.py` 的默认源图，**不要删**；
  删了就只能重新生成、构图不再可复现。被否掉的试点 A 已清理。

## 18. 虎妖移动动画改骨骼（2026-10-26，无新 AI 素材）

用户反馈「走路姿势太奇怪，脚动身体在抽搐」。这是**序列帧的结构性问题**，不是调参能解决的：

| 指标 | 8 帧 walk 实测 | 结论 |
|---|---|---|
| 底边漂移 | 0px | 不是垂直抖动 |
| 逐帧高差 | ≤5px | 没被压扁拉长 |
| **上半身 IoU** | **0.93~0.96** | 每一帧的躯干轮廓都不一样 ← 「抽搐」 |

根因：**每一格都是模型独立重画的一只虎**。加密帧数只会让抽搐更频繁（8 帧抽搐 8 次，
16 帧抽搐 16 次）。提示词改不动 —— 模型没有「同一只」的概念。

### 做法：同一张贴图被关节拖着动

`tools/build_tiger_rig.py` 把**正侧定妆图**拆成 8 块刚体件，`BossRig` 用 Node2D 层级
（不是 Skeleton2D —— 刚体分块用不上骨骼权重，Node2D 更简单可控）驱动旋转：

```
BossRig
└── body（躯干，起伏/俯仰作用在它身上）
    ├── head
    ├── tail1 → tail2        （两节链，尾末段滞后一点，鞭子感）
    ├── leg_far_hind / leg_far_front     z=-3（远侧腿，在躯干后）
    └── leg_near_hind / leg_near_front   z=+2（近侧腿，在躯干前）
```

- **idle / walk 走骨骼，五式招式仍用序列帧**：招式是一次性的、姿态差异大，「逐格重画」
  反而不明显；骨骼化每条招式都要单独 K 帧，不划算。两套素材画布完全相同（1100×820、
  脚底同一基线），出招时隐藏骨骼、显示序列帧，不会错位。
- 步态按真实四足侧序 `LH → LF → RH → RF`（近侧后 → 近侧前 → 远侧后 → 远侧前），
  各差 1/4 周期；躯干 2 倍频起伏 + 1 倍频俯仰，**头反向抵消俯仰**（动物走路时头是稳的）。
- 参数全在 `BossRig` 顶部的常量里（`WALK_CYCLE` / `WALK_LEG_SWING` / `WALK_BOB` …）。

### 切法：圆形关节（这是整套方案的地基）

body 在每个关节处挖一个圆洞，对应部件带一个同心圆盘，**圆盘内的像素只属于部件**。
于是部件转多少度，圆盘都恰好填满 body 的洞，旋转时不会露出背景。

### 六个踩过的坑（都不 obvious）

1. **腿的横向边界必须随 y 变化**。前腿是斜的（膝在 x≈1030、脚掌在 x≈1290），固定区间
   要么切掉腿根（圆盘补不回来，旋转后看到「半个身子」），要么吃到旁边那条腿。
2. **`body` 挖洞要用「未膨胀」轮廓**。按膨胀后的挖，body 会被切成 4 块互不相连的碎块
   （各 600~1250px），腿一转它们就悬在原地 —— 画面上就是「游离的肉」。
3. **部件之间要外溢 1px**。严格互斥时边界两侧 alpha 都被裁到 0，缩放插值后各自变淡，
   拼起来是一条 1~2px 的白缝（臀部、腿根、尾中都有）。
4. **`AnimationPlayer` 的 track 必须写完整路径**。所有部件都挂在 body 下，写 `head:rotation`
   会让它在 rig 根下找不到节点，只报一句 "couldn't resolve track" 然后**整条轨道静默失效**
   —— 表现是「骨骼搭好了但一动不动」，极难查。正确写法 `body/head:rotation`。
5. **`alpha` 阈值 180**。取 60 时 bbox 会被抠图残留噪点撑满整张图，内容高归一算错，
   整套坐标跟着漂（缩放比从 0.73 掉到 0.58）。
6. **摆角别过 10°**。腿块在关节处是折线切边，转得越多切边扫过的面积越大，会从 body 的
   洞边缘露缝。`WALK_LEG_SWING = 0.175`（10°）时这条缝在 scale 0.25 下不到 1 屏幕像素。

## 19. 虎妖赛璐璐化 + 骨骼关节裂隙优化（2026-10-26）

用户两件事：「画风过于写实，要更赛璐璐」+「骨骼动画关节处有裂隙」。

### 一、关节裂隙：三个成因，三个修法

| 修法 | 改动 | 为什么 |
|---|---|---|
| 腿块顶端收窄 | band 的第一行不再沿用腿的真实宽度，而是收到**关节圆盘在该高度的宽度** | 腿块顶部是一条水平切边，转动时这条边扫过的扇形会越过 body 挖的洞边缘。收进圆盘后顶部完全被圆盘覆盖，转动不产生扫描 |
| 尾根圆盘 50 → 58 | `TAIL_R` | 圆盘要略大于尾巴最粗处，否则摆 5° 就有 5px 缝 |
| 摆角设上限 | `WALK_LEG_SWING = 0.175`（10°）、`TAIL_SWING = 0.062`（3.5°） | 摆角越大，切边扫过的面积越大。这是被接缝卡住的上限，不是审美选择 |

代价：圆盘外那点腿根留在 body 里不跟着转（静止时看不出来，因为 body 那圈像素本来就是同一张图），
表现为「腿略微变细」，比露缝好得多。

### 二、画风：后处理做不到，只能重画

先试了纯图像处理（中值保边 + 色阶量化 + Sobel 描边），**失败**：颜色发绿发脏、细节糊成一片。
原因是原理性的 —— 赛璐璐的核心是**重新定义光影为色块**，后处理只能量化已有的连续渐变，
得到的只是「脏掉的写实图」；而且写实图边缘太密（毛发），Sobel 描出来全是噪声。
脚本已删，不要重走这条路。

改用 **AI 重画 + 提示词切风格**：

- `tools/boss_art_prompts.py` 新增 `STYLE_CEL`，按 BOSS 覆盖（`CEL_BOSSES = {"boss_huyao"}`）。
  ⚠ **不能直接改 `STYLE`**：刀客现有 9 套素材是厚涂，改了会新旧打架。谁要卡通化谁登记。
- 赛璐璐提示词的关键是「**同时说要什么和不要什么**」：只写「赛璐璐」模型仍会习惯性加渐变，
  必须显式写「不画毛流细纹、不画写实皮毛的碎笔触、不画高频噪点、不做连续渐变」。
- 背景要求需要**加码到最高优先级 + 结尾重申**：第一张赛璐璐定妆图风格对了但背景被画成白色
  （长提示词把背景要求稀释了），抠图直接失败。现在开头写「最高优先级，不满足则整张作废」、
  结尾再写一遍「就是纯荧光品红 #FF00FF，不是白色」。
- 定妆图刻意**去掉了「妖气墨烟」**：半透明烟雾在赛璐璐里会变成一坨半透明色块，
  而且拆件时软边会和圆盘混在一起。

### 三、换图必须重校解剖参数（新暴露的脆弱点）

赛璐璐重画后虎体形变了（腿更粗短、**近侧后腿右移 70px**），沿用旧坐标的后果是
圆盘落到腿外面、一转身直接断腿。

现在 `tools/build_tiger_rig.py` 的 `LEGS` / `TAIL_SPINE` / `TAIL_EDGE` / `HEAD_POLY`
全部带实测注释。**换图流程固定为**：

1. 抠图，存 `hero_side_*.png`
2. 扫描：`y=620 / 700 / 780 / 860` 上四条腿是独立 alpha 段，读中心与宽度得关节坐标与折线
3. 尾巴：找「刚开始与身体分离」的那一行作为 `TAIL_EDGE` 起点（写晚了 tail1 只剩一小块）
4. 重跑 `python tools/build_tiger_rig.py --src <定妆图>`
5. 看 `rig_preview.png` 的分件着色图 + 拼回自检 IoU（<95% 就是切错了）

脚本已参数化（`--src` / `--out` / `--preview`），换图不必改代码。

### 四、当前状态（待用户决定）

- **idle / walk**：赛璐璐版骨骼（`tiger_rig/` 已换成赛璐璐分件）
- **五式招式**：仍是**写实版序列帧**（`boss_huyao.tres` 没换）

也就是「站着是卡通虎、出招变写实虎」。要彻底统一必须重画招式序列帧：
7 套 × 2 张 = 14 张，约 70~140 积分。提示词已经切好（`CEL_BOSSES` 里有 `boss_huyao`），
重画后走正常的 `split --append` → `compose` → 覆盖 `boss_huyao.tres` 即可。

### 五、招式也改成骨骼（2026-10-26）

用户问「招式能用骨骼吗」。做了一版，**5 招全部骨骼化**，零积分、风格天然统一。

| 招 | 主要表演手段 | 效果 |
|---|---|---|
| slash_single 横扫 | 躯干后拉下沉 → 前扑 + 前倾 + 拉长 | 好 |
| smash 碎岩 | 躯干抬起 → 猛砸 + 压扁 + 余震 | 好 |
| arrow_volley 乱舞 | 躯干左右急甩 | 好 |
| arrow 掷石 | 躯干拱背 → 前送 | 勉强 |
| element_orb 妖丹 | 躯干收 → 猛前探 | 最弱：头是一整块贴图，**没有下颌关节，做不出「张口」**，只能靠妖丹特效补 |

**设计原则：以躯干为主，腿只做辅助。** 躯干是整块刚体，位移/旋转/缩放怎么动都不会露接缝；
腿的摆角受关节接缝限制，**招式里也不能超过约 0.22（12.5°）** —— 实测 25° 时后腿根会露出
一块 20×15 的白色。力量感靠「蓄力后拉下沉 → 爆发前扑 + 挤压拉伸」表达。

⚠ **头的转动在招式里必须压在 1° 级**。head 的 mask 是**多边形**（腿和尾是圆盘），
转 7° 时脖子那条非圆边界会扫出 body 的洞，画面上就是头后面露出一块白色（实测）。
姿态改由躯干俯仰表达 —— 整只虎前倾比「头单独低下去」更像发力，也天然无缝。

**代价（必须如实说明）**：骨骼招式只有关节旋转 + 躯干缩放，**没有肌肉隆起 / 毛发炸开 /
张口**，动作比手绘序列帧「简洁」。换来的是零成本、风格 100% 统一、随时可调时长与幅度。

代码：`BossRig.SKILLS`（每招时长）+ `_make_slash / _make_smash / _make_arrow /
_make_orb / _make_volley`。`play_one_shot` 现在**骨骼招式优先**，序列帧只在骨骼没有
该动画时兜底（兼容未迁移的招式）。

### 六、嘴缺一块（2026-10-26 修）

用户反馈「虎妖嘴缺了一块」。根因不在原图 —— **在 `HEAD_POLY` 的多边形**。

原来的下缘是「嘴角 (1438,478) → (1362,542) → (1300,542)」，等于从嘴角直接斜切到脖子，
把整个嘴的下半部（**下颌 / 獠牙 / 舌头 / 下巴**）切给了 body。head 贴图上就只剩上唇，
游戏里看就是「嘴缺一块」。

修法：多边形下缘沿下颌轮廓走 —— `(1480,498) → (1442,548) → (1398,588) → (1348,592)`。
head 贴图从 223×282 变成 226×318，拼回 IoU 从 96.1% 升到 97.7%。

⚠ **多边形宁大勿小**：取的是 `alpha & polygon`，多边形多出来的部分本来就没有像素，
不会误吞身体部位。反而是画小了才会切掉真实内容。这条对以后的剑客 / 刀客同样适用 ——
描解剖多边形时，**先按「能包住的一切」描，再靠 alpha 收边**，而不是试图精确贴轮廓。

### 七、招式「没有动作，只有放大缩小」（2026-10-26 修）

用户实战反馈。实测（加载 `boss.tscn` 走真实 `_play_form_anim` 路径、逐 0.1 秒打印骨骼姿态）：

```
t=0.3s  pos=(-24, 15)   rot=-0.121  scale=(1.065, 0.925)   ← 蓄力
t=0.4s  pos=(53.5,-14)  rot= 0.215  scale=(0.899, 1.146)   ← 爆发
t=0.5s  pos=(0, 0.007)  rot= 0.120  scale=(0.978, 1.040)   ← 招式结束，但没归位
t=0.8s  pos=(0, 1.015)  rot= 0.120  scale=(0.978, 1.040)   ← 永久卡住
```

**招式一直在播**，问题有两个：

1. **`idle` / `walk` 只写了 body 的 position（呼吸起伏），没有 rotation / scale 轨道。**
   `AnimationPlayer` 播完非循环动画会**停在最后一帧**，于是躯干永久卡在「倾斜 0.12 弧度 +
   变形 1.04 倍」。玩家看到的就是「只有变形、没有动作」。
   修法：两个循环动画各补两条归零轨道（首尾同值），`stop_one_shot` 再手动归零一次做双保险。

2. **蓄力脉动 1.25 倍抢戏**。兽型体量本来就大，全身放大 1.25 倍像充气，而且它是单次
   脉动、幅度最大，盖过了骨骼招式。
   修法：`BossBase.windup_pulse_scale()` 抽成可覆写，人形保持 1.25，`prototype_boss.gd`
   （虎妖）覆写成 1.12。

⚠ **通则**：只要一条属于「某个节点」的属性被任何一条动画轨道写过，**所有循环动画都必须
也写一条归零轨道**。否则播完一次性动画后，该属性会停留在最后一次写入的值上。
这次是 body 的 rotation/scale，下次可能是任意节点的任意属性。

### 八、招式时间曲线重排（慢-蓄-爆-停）

原来关键帧均匀排开，动作是匀速滑过去的 —— 视觉上像「挪」不像「打」。横扫已改成：
蓄力 38%（0.225 秒走 28px）→ 蓄满定住 0.02 秒 → 爆发 6%（0.03 秒走 80px，速度是蓄力的
9 倍）→ 打击定格 0.05 秒完全不动 → 缓慢回收。

**「定住」用两个相邻且同值的关键帧做**（CUBIC 在同值 key 之间是平的），只靠「值变化小」
停不住。其余四招待按同一原则重排。

### 九、骨骼招式「根本没动」（2026-10-26 修，第五节的前提错了）

用户第三次反馈：「虎妖释放技能时骨骼根本就没有动，例如释放虎爪时要挥动前腿和前爪一系列动作」。

**真因：`prototype_boss.gd` 从来没有调用过动画播放。**

虎妖的技能不走 `domain_boss_01.gd` 的 `_begin_skill`（那里面调了 `_play_form_anim`），
而是走自己的 `_on_attack_windup(kind)` → 只有 `_show_windup(color)` → `_tween_pulse`。
整套骨骼动画**一次都没被触发过**，实战里只有「整体放大 1.12 倍 + 躯干缩放」——
这正是「只有放大缩小、没有动作」。

⚠ **为什么上一轮没查出来**：我验证时直接调 `boss._play_form_anim("form_slash_single", 0.7)`，
绕过了真实入口，于是「动画能播」这个结论建立在错误的前提上。
**教训：验证必须从玩家能触发的那个入口开始**（`_begin_attack(kind)`），不能直接调下游函数。

修法：新增 `FORM_OF_KIND`（攻击类型 → 招式形态 id）+ `_play_kind_anim(kind)`，
在 `_on_attack_windup` 末尾调用；踏地在 `_start_smash` 里单接。

### 十、连带的四个 bug（都只在真实路径下才现形）

1. **`play_one_shot` 的防重挡住了同一招的第二次**
   `if _one_shot == anim: return true` —— `_one_shot` 由 SkinVisual 的倒计时清，
   而那个倒计时只管序列帧，BossRig 的 `_one_shot` 永远不清。第一发之后再放同一招，
   直接被拒。改成「只有在播、且就是这一招」才跳过。

2. **归零轨道又漏了腿**（第二次踩同一条铁律）
   `idle` / `walk` 只给 body 补了 rotation/scale 归零，腿没有。收招后 `leg_near_front`
   永久卡在 -0.36 弧度。改成 `_neutral_all()`：遍历**所有部件**，用 `find_track` 查重，
   缺 rotation / scale 轨道的补一条首尾同值的。⚠ 不能无脑全补 —— 同一属性两条轨道，
   后加的会盖掉正弦摆动。

3. **CUBIC 插值过冲把腿甩到 -1.02 弧度**（设定 -0.68，超出 50%）
   「0.04 秒内从 +0.34 甩到 -0.95」这种急变上，CUBIC 会严重过冲，而且过冲会拖进
   后面的定格段 → 定格时腿在抖，正好毁掉 hit-stop。
   改：**旋转轨道一律 LINEAR**，位移 / 缩放保留 CUBIC（它们的过冲是「更有力」）。

4. **腿的切法不支持大摆角**（设计缺陷，见下）

### 十一、腿从「12.5°」放开到「54°」：切件换成真圆盘关节

旧切法是「`y >= cut` 的一条带 + 关节圆盘」。带的上边界是一条**水平切边**：
腿转 θ 度，这条边扫过的区域越出 body 挖的洞 → 露白缝（实测 10° 就有 5~8px）。
所以摆角被压在 12.5° 以内，爪尖位移不到 3 屏幕像素 —— **等于没有挥爪**。

新切法：**腿 = 「整个关节圆盘里的全部前景」∪「圆盘下沿以下的腿身」**。
腿的上边界变成圆弧本身，圆弧绕自己的圆心旋转形状不变，body 挖的正是同一个圆，
于是**转任意角度都恰好填满**。代价是圆盘里那块躯干肉会跟着腿转（赛璐璐平涂 +
游戏里只有十几像素，看不出来）。

同时把**前腿关节从髋部上移到肩部**（`jo` y 620→578，`r` 66→80）：
摆臂长度从约 200px 变成约 340px，同样角度下爪尖位移近乎翻倍。

### 十二、小尺寸是硬约束：动作幅度要按「显示像素」倒推

Boss 在游戏里是 **277×142 屏幕像素**（内容高 560 × scale 0.25），前腿只有约 35px 长。
任何关节动作在此尺寸下都会被压扁。所以幅度不能凭「原图看着够」定，要倒推：

```
爪尖位移（屏幕像素） = 摆臂长 × sin(摆角) × 内容缩放(0.716) × 显示缩放(0.25)
肩部摆臂 340px、摆 54°(0.95rad) → 340 × 0.813 × 0.716 × 0.25 ≈ 49px
```

**经验阈值：小尺寸下爪尖位移 ≥ 20 屏幕像素才看得出「在挥」**，换算回来就是
摆角 ≥ 0.6 弧度（34°）。这就是为什么 0.24（14°）完全无效、0.68（39°）勉强、
0.95（54°）才够。

### 十三、五招统一节奏（慢-爆-停）

| 招 | 时长 | 表演主体 | 近侧前腿 |
|---|---|---|---|
| slash_single 虎爪裂空 | 0.80 | 躯干后拉 → 前扑 + 拉长 | +0.34 → **-0.95** |
| smash 猛虎踏地 | 0.85 | 躯干抬起 → 猛砸压扁 | +0.55 → -0.12 |
| arrow 碎岩飞砂 | 0.78 | 拱背 → 前送 | +0.40 → **-0.60** |

### 十五、关节白缝（2026-10-26 修，第五节方案的直接代价）

用户反馈「现在骨骼关节有裂隙了」—— 是我把腿的摆角从 12.5° 放到 54° 之后出现的。

**先纠正一个诊断错误**：用「内部空洞面积」当指标不可靠。
`binary_fill_holes` 会把「被腿围住的正常背景缝隙」也算成洞，所以 rest 帧测出 2882px
（那是尾巴与身体之间本来的空隙），而摆角变小时数字反而变大 —— 数字和肉眼看到的
严重程度不对应。**判断要看 1:1 放大图，并且和 rest 基准帧对比。**

**根因是 2D 刚体分块的固有矛盾**，不是 bug：

| 做法 | 结果 |
|---|---|
| body 挖掉腿（含腿身） | 腿身转走后原位置空一块，**露出背景 = 白缝**，边缘还是 mask 的硬直角 |
| body 保留腿身（只挖圆盘） | 腿转开时露出 body 里那份腿 → **四条灰扑扑的残影腿**，比白缝更难看 |

两者不可兼得。四条路都试过，记录如下，别再重走：

1. **只挖圆盘 + inpaint 腿身成躯干色** → inpaint 只换颜色不改形状，残影腿的轮廓还在
2. **腿根保留（躯干轮廓 +N px 内的腿像素留在 body）** → 有用但有限；N=110 比 N=60 更差
   （保留区伸到躯干外，白缝反而更宽）。最终取 N=60，白缝面积 −60%
3. **圆盘自动收窄到「内部全实体」**（`safe_disk_radius`）+ 圆盘内背景用最近色填充
   （`fill_disk_holes`）→ 消除「圆盘内的小缺口」，但不解决圆盘外的腿身洞
4. **body 挖洞形状高斯平滑（sigma=4）** → **这条是真解**，见下

**真正有效的两步**：

- **挖洞形状高斯平滑**：腿的 mask 边界是折线（band 左右界 + cut_y 水平线），直接在
  body 上挖洞就会留下硬直线和直角；腿一转开，这些直角露在背景里，看着就是「裂了一条线」。
  `gaussian_filter(hole, sigma=4) > 0.5` 把折线抹成圆角，视觉上像自然缝隙，
  顺带让洞比腿小一点（腿的边缘能盖住洞口）。拼回自检 IoU 97.72% → **99.51%**。
- **摆角回到「洞不可见」的区间**：招式 0.34（19.5°，爪尖约 19 屏幕像素），
  走路 0.12（7°）。⚠ 走路被压得比招式狠得多，因为走路是常驻动作、缝一直存在，
  而招式是瞬间的。

**教训（写进 MEMORY.md）**：2D 刚体分块里，「部件转走后原位置空一块」没有通解。
能做的只有三件事 —— 圆盘内保证全实心、洞口边缘平滑、摆角控制在洞不可见的范围。
想要「大幅挥动且绝对无缝」，只能走骨骼形变（mesh deform）或逐帧手绘，不是调参能到的。

## 20. 刀客人形骨骼（2026-10-26，无新 AI 素材）

**不重画**。理由和虎妖赛璐璐那次一样 —— 序列帧逐格重画必然导致躯干抽搐，
而人形比兽型更经不起躯干帧间差异。整条管线是「定妆图 → 拆刚体件 → 关节驱动」，

`leg_back`（髋为轴）。刀不单独拆 —— 刀柄握在手里，拆开必然「握不住」。

### 20.1 踩过的四个坑（都很难从现象反推）

**① 子类不能重定义父类常量。** `BossRigHuman` 里写 `const IDLE_CYCLE := 3.2`
直接 **parse error**（`The member "IDLE_CYCLE" already exists in parent class BossRig`），
整脚本解析失败 → `SkinVisual` 静默回落四足骨骼 → 人形 BOSS 用虎的招式表，
表现是「出招时人不动、只有飘字」。人形参数一律加 `H_` 前缀。
父类另行加 `_skill_ids()` 虚方法，子类只换招式表、不复制 `_build_animations`。

**② 头不能单拆。** 第一版照虎妖思路拆了 `head`（颈为轴），`HEAD_POLY` 只圈住一小块，
剩下大半个头留在 body 里 —— 头一转画面上就有**两个头**。人形的头本来只做 1° 级微动，
收益抵不上风险，**头并入躯干**。

**③ 手臂要分两半处理。** 分界线是「这块部件下面是身体还是背景」：
压在躯干上的 → body 保留轮廓 + 最近色重涂（`inpaint`）；压在背景上的（刀身探出头顶、
拳头伸到身侧）→ body 挖掉，否则挥刀后原位留一片悬空残影。腿永远挖洞
（腿本身就是那里的轮廓，留着就成「鬼影腿」）。

**④ 刀的多边形上缘必须在下缘之上。** 这个环是「先画上缘、再倒着画下缘」，
两条边一旦交叉，`ImageDraw.polygon` 会填出乱七八糟的形状 —— 实测表现是
「头顶被啃掉一块、丸子头飘在空中」。改点前先确认同 x 的两个点 y 上小下大。

### 20.2 打击时刻必须换算，不能直接抄 windup

动画被 `play_one_shot` 压进 `windup + 0.15` 秒（`speed_scale = length / (windup+0.15)`），
所以「伤害判定那一帧」在**动画时间轴**上是

```
t_hit = windup × length / (windup + 0.15)
```

第一版把 windup 当秒数直接写进关键帧，爆发段被排到动画长度之外，永远播不到 ——
表现是「挥到一半就收刀，刀从没砍到人」。短招差 15%，`guard_charge`（前摇 3 秒）差 30%。

### 20.3 一次性动作的收尾不能只看计时器

`SkinVisual` 用 `_process(delta)` 倒数结束招式，而 delta 是**引擎帧时长**；
首帧（进场 / 卡顿 / 从主城切战斗）delta 可能 0.18 秒，计时器一下少掉 18%，
动画只推进 15% —— 两者错位后计时器先归零，**「爆发 + 打击定格」整段被吞掉**
（实测横斩肩角只到 +0.48，设计值 +1.05）。现在骨骼招式以 `BossRig.one_shot_finished()`
（播放头到底）为准，计时器只做兜底（超时 0.35 秒强制收）。

### 20.4 刀气从刀尖出

`rig.tres` 的 `muzzle` 表登记 `palm_project → arm / (188, -118)`（刀尖，从分件 alpha
实测最右点，重跑脚本自动更新）。`domain_boss_01._fire_blade_qi` 改用
`muzzle_position(skill_id)` + `_aim_from(spawn)`（本轮回填到 `BossBase`，虎妖那份上移）。

## 22. 刀客走路缝隙与挥刀幅度（2026-10-26 第二轮）

用户要求：**走路尽量减少关节缝隙、攻击要大幅挥刀**。

### 22.1 缝隙的真凶：腿洞不是圆

走路时裙摆里出现两片楔形裂缝。根因不是"圆盘不够大"，而是**洞的形状**：

```
body 的腿洞 = 整条腿的轮廓（圆盘 ∪ 折线带）
腿 = 同一套形状，绕髋转
→ 圆盘部分永远盖得住（圆绕圆心转），折线带那半截盖不住 → 楔形裂缝
```

**只有圆能自覆盖。** 所以洞要按「洞外面是什么」分两种挖法：

| 区域 | 挖法 | 理由 |
|---|---|---|
| 髋部（裙摆里，圆盘半径内） | **只挖圆盘** | 圆洞任何角度都被圆盘盖满 → 零缝隙 |
| 圆盘以下（裙摆外） | 按腿形挖 | 露出来的正好是**背景**，看不出来 |

一句话：**洞只在"洞外面是背景"的地方才允许是腿形。**

另外两处同类问题一起修了：

- **圆盘必须整块不透明**：圆盘里原本可能有透明的缝隙（两腿之间那点背景），而
  `fill_disk_holes` 只补 `alpha<40` 的像素，半透明边缘会漏过去 → 漏光成楔缝。
  写盘时把圆盘区域强制 `alpha=255`。
- **靴尖要盒子兜底**：折线带在靴尖/靴跟漏几像素，漏掉的那片留在 body 里，
  腿一摆就成了「飘在地面的鞋尖」。补一个只覆盖裙摆以下的包围盒。

### 22.2 头顶那撮头发：arm 和 body 都要留

大幅挥刀（130°）时头顶会出现一个**飘着的球** —— 刀身从丸子头下面穿过，
多边形把头发切成两半：上半在 body、下半在 arm，arm 一转下半带走、上半悬空。

修法是**两边都留**（`HAIR_KEEP_ZONE`）：arm 里留着保证刀身不被切缺口；
body 里也留着（重涂）保证挥刀时头发不会跟着走。只留一边就会出问题。

### 22.3 挥刀幅度（用户要求「大幅」）

| 招式 | 旧肩角 | 新肩角 | 总摆角 |
|---|---|---|---|
| 横斩 | −0.45→+1.05 | **−0.85→+1.42** | 86° → **130°** |
| 沉步竖斩 | −1.35→+1.55 | **−1.62→+1.86** | 166° → **199°** |
| 破步突进斩 | −0.30→+0.95 | **−0.72→+1.32** | 72° → 117° |
| 封路刀域 | −0.85→+1.62 | **−1.12→+1.88** | 142° → 172° |
| 刀气追击 | −0.20→+0.80 | **−0.58→+1.18** | 57° → 101° |
| 满势断岳 | −1.60→+1.70 | **−1.88→+1.98** | 189° → **221°** |

同时把躯干俯仰放大（横斩 −0.10→+0.13）与位移加大，让**整个人**跟着甩，

## 23. 出招时间轴改成「按真实秒编排」（2026-10-26 第三轮）

用户第二次反馈「释放技能时需要大幅的挥刀动作」—— 上一轮已经把肩角从 86° 放大到 130°，
**但幅度不是问题所在**。按玩家入口逐帧抓了一次出招，帧序列暴露了真相：

```
f00~f37（38 帧）  举刀蓄力，肩角 0 → −0.85
f38              −0.33      ← 挥砍
f39              +0.54      ← 挥砍
```

**挥砍只有 2 帧**。60 帧下 2 帧就是 0.03 秒，眼睛只看到一闪，
根本读不出「挥」—— 玩家看到的是"BOSS 胀大了一下然后闪了一下"。

### 23.1 根因：时间轴是按「动画秒」写的，而动画会被压缩

动画被 `play_one_shot` 压进 `windup + 0.15` 秒播放（`speed_scale = length / (windup+0.15)`），
所以「动画里的 0.04 秒」在真实世界里根本不是 0.04 秒。旧代码把「爆发 0.04 秒」
当成真实时间写进关键帧，实际只有 2~3 帧。

**修法：所有阶段按真实秒编排，再用 `_real_to_anim()` 换算回动画秒。**

```
0    → 0.50W    蓄力（慢，让玩家看清"在准备"）
0.50W → 0.85W   挥砍：0.35W 秒的**可见挥击**（W=0.85 时 0.30 秒 ≈ 18 帧）
0.85W → W       定格：刀压在最低点，伤害在停顿里落下
W    → W+0.15   收招
```

挥击**早于**判定结束（0.85W < W）：刀先到位、停住，伤害在停顿里落下 ——
既有打击感，又不会出现「刀还在飞、伤害先到」。

### 23.2 肩臂的加速曲线

肩角用 LINEAR（项目铁律：CUBIC 在急变上会过冲 50%），所以「慢起—快收」靠**关键帧位置**做：
在挥击段的 42% 处插一个只走了 25% 行程的中间帧 → 前段慢、中段最快、到顶急停。

### 23.3 蓄力脉动调低

`windup_pulse_scale()` 基类默认 1.25（兽型的「充气」感），刀客改成 **1.15**。
脉动太夸张会把主表演盖掉 —— 玩家看到的是"BOSS 胀大了一下"，而不是"它把刀抡圆了"。

### 23.4 ⚠ 改这套时间轴时踩到的坑

- **`_extra_loops()` 钩子被脚本补丁误删**：`--headless -e --quit` **抓不到继承/覆写类错误**
  （项目记忆里早有这条），只有真跑场景才报 `Function "_extra_loops()" not found in base self`。
  改完一定要跑一次真实场景，不能只看解析检查。
- `_strike` / `_legs` / `_shawl` 的第二个参数从「判定时刻」改成「**动作名**」，
  因为换算成动画秒需要 length 与 windup。调用点要同步改（剑客那边漏了三处，
  运行期才报 `argument 2 should be "String" but is "float"`）。

## 24. 「正常挥刀」：肩角要按**刀尖的屏幕方向**定（2026-10-26 第四轮）

用户第三次反馈「要正常挥刀，现在的挥刀动作太奇怪了」。这次不再凭感觉调参，
改成**先量、再定**。

### 24.1 根因：肩角 ≠ 刀的方向

刀客静止姿势是**扛刀在肩**，刀尖指向右上 ≈ −32°（相对肩关节）。
所以「肩角 = 0」**不等于**「刀指前方」；而且躯干还有俯仰，肩是 body 的子节点，
躯干一转，刀尖在屏幕上的方向还会再变一次。

前一版的问题：所有招式都用了同一条「举过头顶 → 砸到斜下 49°」的巨弧 ——
**横斩的收尾竟然是竖劈的角度**，七招全是同一条螺旋桨轨迹，看着当然怪。

### 24.2 量法（可复用）

```gdscript
# 刀尖 = 持刀臂分件的 muzzle 锚点（刀客是肩 + (188, −118)）
var tip: Vector2 = arm.to_global(Vector2(188.0, -118.0)) - rig.global_position
var ang: float = rad_to_deg(atan2(tip.y, tip.x))   # 屏幕上的刀尖方向
```

实测静止 −53.7°（相对 rig 原点；相对肩关节是 −32°，两者差在肩的位置）。
命中姿态附近的经验换算：`screen ≈ −21.3 + (arm − 0.53) × 65°`（躯干俯仰 ≈ +0.15 时）。

### 24.3 定稿：每一招的刀尖方向

| 招式 | 举刀时刀尖 | 命中时刀尖 | 肩角（起 → 止） | 弧线 |
|---|---|---|---|---|
| 横斩 | −112°（右上后） | **+4°（正前）** | −1.15 → +1.04 | 116°，平扫 |
| 沉步竖斩 | −105°（过顶） | **+46°（前下）** | −1.19 → +1.55 | 151°，下劈 |
| 破步突进斩 | −100° | +5° | −1.10 → +0.93 | 105°，低扫 |
| 封路刀域 | −100° | +60° | −1.15 → +1.78 | 160°，斜插地面 |
| 刀气追击 | −100° | +8° | −1.12 → +0.98 | 108°，平扫出剑气 |
| 满势断岳 | −117°（大回旋） | +40° | −1.55 → +1.47 | 157°，大回旋劈 |

**判据：弧线形状要符合招式名** —— 横斩是平扫（终点接近水平）、竖斩是下劈（终点斜下）、
封路刀域终点最陡（插地）。幅度仍然可观（105°~160°），但读起来是「斩」不是「转」。

### 24.4 附带：躯干要跟上

肩角是「刀」的动作，躯干俯仰是「人」的动作，两者要配合：
横斩躯干 −0.14 → +0.19（转体带动劈砍），满势断岳 −0.15 → +0.19。
只动肩不动腰，刀就像装在别人身上的。

## 25. 「正向自然挥刀」：横扫不再绕到脑后（2026-10-26 第五轮）

用户反馈「现在是反正挥刀的，因为扛着刀在肩上，要正向自然向前挥刀，可以逆时针斩出来」。

### 25.1 根因：横扫的蓄力绕到了脑后

刀客静止扛刀在肩（刀尖右上 ≈ −32°）。第四轮的横斩 `arm_back=-1.15` 会把刀先甩到
**头顶后方**（刀尖 ≈ −112°），再绕头顶一圈砸到正前 —— 玩家看到的第一下动作是
「刀往后绕过头」，这就是「反着甩」的来源。**横扫招式根本不该绕到脑后。**

### 25.2 修法：横扫只在身前半球运动

| 招式 | 旧肩角 | 新肩角 | 刀尖路径 |
|---|---|---|---|
| 横斩 | −1.15 → +1.04 | **−0.45 → +1.40** | 正上 −75° → 前下 +28°（实测） |
| 破步突进斩 | −1.10 → +0.93 | **−0.40 → +1.25** | 上 −68° → 前平 +18° |
| 刀气追击 | −1.12 → +0.98 | **−0.45 → +1.30** | 上 −72° → 前平 +22° |
| 满势断岳 | −1.55 → +1.47 | **−1.35 → +1.55** | 收小蓄力幅度 |

实测横斩刀尖：−53.7°（静止）→ −75°（举到正上）→ **+28°（正前下）**，
全程在身前半球（−75°~+28°），不再有绕头顶的反向甩动。
竖斩/封路/满势是下劈，举过头顶再砸是正常劈砍，保留。

### 25.3 「逆时针」与镜像

BOSS 朝左（scale.x=−1）时这条顺时针弧翻成**逆时针**，正好是用户描述的方向。
不需要单独为镜像做一套数据。

## 26. 刀客肘关节：前臂拆件 + 鞭打挥刀（2026-10-26，无新 AI 素材）

用户第六次反馈「挥刀时扛在肩上直接向下挥，不符合人体动作」。根因：整条臂焊死成
单段刚体，挥刀只能是「刚体绕肩转」。真人发力是**肘先收 → 手领先甩出 → 刀跟随**
（鞭打），必须有肘关节。

### 26.1 拆件（build_daoke_rig.py）

- `arm` 拆两块：上臂（肩盘）+ `arm_fore`（前臂 + 拳 + 刀，parent=arm，关节=肘）。
  刀身整条归前臂（手握刀），muzzle 锚点改挂 arm_fore、相对**肘**。
- 肘盘 = 与腿/肩相同的实心圆盘零缝做法。**盘心选点实测**：首选 (381,315) 落在
  肘弯外侧的**背景缝**（臂与斗篷之间），`safe_disk_radius` 缩到下限 16，前臂一转
  上臂截口必露缝。网格扫描后取 **(400,300)**（肘窝皮肤实心区 r=32、离护腕轴 18px，
  盘能整体吞掉护腕下端）。换定妆图必须重扫。
- body 的挖除/补画按**整条臂**（arm ∪ arm_fore）算，静止帧拼回 IoU 99.49%。

### 26.2 两个参照系口径坑（同一次构建踩到）

1. `part_joint` 是**相对 rig 原点（画布中心）**的全局关节坐标；挂到父节点下时
   由 `BossRig._build_nodes` 自己减掉父关节（`pos -= part_joint[parent]`，boss_rig.gd:152）。
   ⚠⚠ 本轮误记成「相对父关节」、给 arm_fore 写了 `ELBOW - SHOULDER = (-28,+48)` ——
   **这是错的**，引擎把肘放到画布 (422,408)（腰的高度），前臂 + 刀整体下垂 108px，
   所有挥刀都绕错轴转。正确写法见 §27（换定妆图重跑 `build_daoke_rig.py` 时别再犯）。
   腿/上臂的父恰好是 body（关节就在画布中心），减不减都一样，所以这个坑以前从没暴露。
2. `part_offset` 是「贴图中心相对自身关节」的**纯向量**，两边都用相对画布中心
   相减，与父链无关；预览/自检拼回要用关节的**画布坐标**。

### 26.3 鞭打编排（boss_rig_human.gd）

`_strike` 加三个**默认值尾参** `elbow_back / elbow_whip / elbow_hit`
（剑客按位置调用不受影响；`_add_keys` 对没有 arm_fore 的 rig 静默跳过）：

- t_pull：肘折到 elbow_back（负 = 折臂收刀，比肩的举刀多收一截）。
- t_mid：肘冲到 **elbow_whip**（此刻肩才走 25%）→「手领先甩出」。
- t_swing：肩追上，肘相对回摆到 elbow_hit →「刀最后到位」；定格盖过判定帧。

elbow_hit **不是插值**，是「过冲后回摆」的落点，按几何反解：
命中刀指向 = −32°（刀尖静止方向）+ 肩角 + 肘角。六招数值：
横斩 −0.38/+0.55/−0.22，竖斩 −0.10/+0.50/−0.11，破步 −0.34/+0.55/−0.16，
封路 −0.12/+0.55/−0.08，刀气 −0.38/+0.50/−0.16，满势 −0.18/+0.65/−0.09。
guard_charge 手动补肘轨道（架刀 0.35 → 推出 0.55）；idle/walk 各加一条轻正弦。

> ⚠⚠ **本节数值已全部作废**：它反解用的是「刀尖静止 −32°（相对肩）」，而肘关节拆出来后
> 参考系变了；更要命的是 §26.2 那条口径错，肘在腰上，这套编排是在错轴上调出来的。
> 现行设计（先定刀尖朝向再反解肩肘、`elbow_whip` 删除）见 **§27**。

### 26.4 验证

1. Python 直接模拟父子链旋转（arm_fore 绕肘 ±90°、蓄力/挥砍组合姿势）：
   零缝、无断肢，静止帧与原图一致。
2. Godot 自动断言 39 项全过：部件/父子/关节值、六招肘轨道 6 键、whip>hit、
   归零轨道、播放头走完、收招回中性。
3. 窗口模式逐帧截图（`vibe_images/boss_work/boss_daoke/elbow_f*.png`）：
   蓄满折肘（刀举头前、肘弯）→ 挥砍中段刀横扫身前 → 命中刀指前下 → 定格
   与上一轮一致（仅肘回勾 12°）。

> ⚠ 上面第 2、3 条验的是**部件存在、轨道键数、拼接零缝**，验不出「肘关节摆在腰上」，
> 所以断言全绿而玩家仍说动作错。根治办法是 §27 的离线渲染器。

## 27. 刀客挥刀第八轮：肘关节口径纠正 + 先定刀尖朝向再反解（2026-10-26）

§26 之后玩家仍反馈挥刀不对。这轮查到两个根因，其中第一个属于**素材几何摆错**，
在它修好之前调任何角度都是白费：

> ⚠ **§27.2 的「静止指向 −37.5°」与 §27.2 / §27.3 表里的全部角度数值已作废** ——
> 定妆图换成垂刀式之后静止指向变成 **+70.0°**、肩肘的**正负号整个反过来**，现行数值见 §28。
> 没变的是两件事：**先定刀尖朝向、再反解肩肘**这个方法，以及 `part_joint` 走全局口径。

### 27.1 根因①：rig.tres 的 arm_fore 关节写到了腰上

- 现象：前臂 + 刀整体下垂约 108px，「扛刀在肩」变成「持刀在腰」，挥刀绕错轴转。
- 原因：按 §26.2 那条错误口径给 arm_fore 写了相对父关节的 `(-28,+48)`；
  `BossRig` 拿到的是「相对 rig 原点」的坐标，于是肘落在画布 (422,408)。
- 修法：`tools/build_daoke_rig.py` 统一写全局关节 —— arm_fore 的 `part_joint`
  = `ELBOW - 画布中心 = (400,300) - (450,360) = (-50,-60)`，重生成
  `assets/characters/boss/daoke_rig/rig.tres`（现值见该文件 `part_joint` 第 5 项）。
- 脚本注释里已把这条坑写明，换定妆图重跑时照注释走。

### 27.2 根因②：设计顺序反过来——先定刀尖朝向，再反解肩肘

刀尖静止指向 **−37.5°**（相对肘，由 rig.tres 的 muzzle 偏移 (216.73,−166.18) 算出）。
任意时刻：`刀尖朝向 = −37.5° + 躯干俯仰 + 肩角 + 肘角`。

每招只指定「蓄力朝向 / 命中朝向」两个目标，总旋转 = 目标 − (−37.5°)；躯干俯仰先定，
剩下的分给肩肘。**肩肘怎么分都不影响刀尖朝向，只决定手肘摆在哪**——
蓄力时肩多抬 + 肘折起（刀收到头顶微偏后），命中时肩到位 + 肘近伸直。

| 招式 | 肩角 起→止 | 肘角 起→止 | 躯干俯仰 | 刀尖：蓄力 → 命中 | 弧线 |
|---|---|---|---|---|---|
| 横斩 | −0.65 → +0.55 | −0.30 → +0.18 | −0.14 → +0.19 | −100° → **+15°** | 身前斜斩，不绕头 |
| 沉步竖斩 | −0.80 → +1.25 | −0.34 → +0.20 | −0.13 → +0.17 | −110° → +55° | 过顶下劈 |
| 破步突进斩 | −0.60 → +0.55 | −0.28 → +0.30 | −0.12 → +0.15 | −95° → +20° | 身前低平扫 |
| 封路刀域 | −0.85 → +1.50 | −0.33 → +0.29 | −0.09 → +0.12 | −110° → +72° | 高举插地 |
| 刀气追击 | −0.65 → +0.50 | −0.34 → +0.34 | −0.10 → +0.13 | −100° → +18° | 身前平扫 |
| 满势断岳 | −0.95 → +1.30 | −0.34 → +0.21 | −0.15 → +0.19 | −120° → +60° | 大幅下劈 |

横扫类（横斩/破步/刀气）只在身前半球走，不绕脑后；下劈类（竖斩/封路/满势）保留过顶。
BOSS 朝左时 `scale.x = −1`，顺时针弧自动翻成逆时针，不用做镜像数据。

### 27.3 编排简化与其余动画

- `_strike` 的 `elbow_whip` **删除**，只剩 `elbow_back / elbow_hit`；「手领先于肩」
  改由中段配比表达：t_mid 时肩只走 25%、前臂走 55%。旧版在错几何上叠「冲过再回摆」
  的花活，观感更乱。
- `guard_charge` 不套 `_strike`，手动轨道：架刀 肩 0.85 / 肘 0.11（刀指前下 +15°，
  横架在胸口）→ 推出 肩 1.05 / 肘 0.30（刀压到 +42°）。
- idle 前臂轻正弦 = `H_IDLE_ARM×1.6` ≈ 0.022 rad、walk = `H_WALK_ARM_SWING×0.9` ≈ 0.032 rad，
  与肩带相位差/反相，肘关节保持「活」。

### 27.4 新增离线渲染器 `tools/render_rig_pose.py`

之前几轮「自动化检查全过、玩家却说动作错」的根因：只在 build 脚本的预览坐标里画图，
从没按 `BossRig._build_nodes` 的真实口径拼过。这个脚本严格复刻父子变换
（`part_joint` 全局 → 挂父时减父关节；贴图中心落在 `part_offset`；绕自身关节旋转），
**不进 Godot 就能看到引擎里真实会出现的姿态**，用来在改角度前先确认关节摆在哪。


⚠ 默认输出到**项目根**的 `tmp_pose.png` / `tmp_daoke_grid.png`；`.gitignore` 已加
`/tmp_*`，要留档就自己移到 `output/` 下（项目根不留散件）。

## 四十四、苍澜大陆边界整改：外缘林带 / 接缝地垫 / 四区角补片（2026-11-02）

### 44.1 问题诊断

实机截图（`tools/capture_world_edges.tscn`）暴露出三个**独立**成因，不能靠加一层雾遮：

1. **林带贴图被拉伸 + 折叠**：`region_band.gdshader` 旧 UV 写 `(cell+f)/repeat_count`，把 878 世界像素宽的贴图拉到整条带子上再按格折 7 次 → 格边界一条硬折痕、全带糊一档（正是「树比草糊」的来源）。
2. **接缝地垫是照片糊条**：早期用图生图过渡条 + sigma 85 模糊，铺在原生密度的地面上永远读成一层雾。
3. **四区交角**：四条接缝带在 (0,0) 各自 `end_fade` 到约 50% alpha，地形板块的直边从半透明缝里透出来，形成十字硬线。

### 44.2 着色器（`assets/shaders/region_band.gdshader`）

- 长轴按原生密度平铺：一格 = 一个贴图周期；`mirror` 奇偶翻转，在格边界取样连续。
- `warp_amp`：格内连续域位移，`sin(πf)` 在格两端归零，只打散周期、不破坏镜像边界（不能用逐周期常数，格边界会跳变）。
- `carve_low/high`：短轴内缘按双频噪声咬舌形；`end_fade_low/high`：长轴两端收口。
- ⚠ 注释里钉死了「不能写 `(cell+f)/repeat_count`」的教训。

### 44.3 素材烘焙（`tools/prep_world_edges_2026-11-02.py`）

- **8 张外缘林带**（1536×818 / 818×1536）：丹霞北/西、幽冥南/西用石缘源图；青岚南/东、云隐北/东用林冠边源图，按边旋转/翻转、`_match_side` 对色活动区、`_inner_feather` 内缘渐入、`_outer_fade` 外缘带噪声淡出 + 压暗；云隐一套再压冷压暗（`mul 0.78 / desat 0.18 / 冷 tint`）。
- **4 张接缝地垫**（1536×735 / 735×1536）：`build_seam_tiles` 直接缝两侧**真实地面 tile**。`_tile_blend` 对同一张 tile 取 0°/90°/180° 三个循环窗口按三次方噪声权重混合，打散 512px 母题；边界用 6 阶低频噪声 + 24 阶锯齿推成舌形。`_depth_feather` 只羽化短轴两端 —— 长轴是 repeat 方向，烘端部淡出会变成每周期一条透明缝。
- **1 张四区角补片**（1536²）：`build_corner_fourway` 以右图四象限（左上丹霞 / 右上云隐 / 左下幽冥 / 右下青岚）噪声象限混合，中心 alpha=1、半径约 439 世界像素处淡到 0。

### 44.4 世界接线

- `SecretWorldDB.CORNER_CAPS` 登记交汇点与贴图；`secret_world.gd` `_build_corner_caps` 只在四个象限全被已解锁区域占满时铺 `TextureRect`（`EXPAND_IGNORE_SIZE` / `STRETCH_SCALE` / `TEXTURE_FILTER_LINEAR`）。
- 层级：地形 0 → 林带/侧视缝带 1–2 → 接缝地垫 3 → 四区角补片 4。宽镜截图 `output/edges_corner_center.png` 的十字硬边已消失。
