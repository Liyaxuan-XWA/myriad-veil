# HD-2D 改造可行性分析（❌ 已否决）

> ## ❌ 本方案已否决（2026-10-18 用户决定）
> **最终选择：保持纯 2D，不做 HD-2D 改造。**
>
> 否决原因：即时战斗依赖精确的距离与朝向判断（弹刀窗口仅 0.22s、必须站定），
> 斜俯视角会引入透视误差与景深干扰，与核心战斗手感冲突；本项目的战斗体验优先级高于画面立体感。
>
> **本文件仅作决策留档**，用于说明「为什么不转 HD-2D」，避免后续重复讨论。
> 其中所有 3D 相关内容（`Sprite3D`、`forward_plus`、相机、光照）**均不实施**，不要作为开发依据。

> 分析时间：2026-10-18 · 基于当时代码库实测数据
> 当时结论：技术上可行且时机极好，但存在一个必须先解决的设计矛盾（不是技术问题）。

## 〇、先澄清：你说的「HD-2D」是哪一种

这个词目前有两种常见用法，成本差 5 倍以上，必须区分：

| 说法 | 含义 | 代表 | 本质 |
|---|---|---|---|
| **A. 立体 HD-2D** | 3D 场景 + 2D 角色立绘 + 景深/移轴，角色有真实地面投影 | 八方旅人、三角战略 | **表现层 3D 化，逻辑层仍 2D** |
| **B. 高清 2D** | 还是纯 2D，但美术规格提高（高分辨率、精细立绘、多层视差背景） | 圣剑传说重制 | 只换素材，不动引擎架构 |

本文按 **A** 分析（因为你提到「转换为 HD2D」，且项目是彩色块占位，说明你期待的是质变而不是分辨率提升）。
如果你要的其实是 B，那答案简单得多：**当前架构已经支持，只需把 `art_db.gd` 里的占位色块换成正式贴图，零代码改动。**

## 一、可行性判断：分维度打分

| 维度 | 现状（实测） | 改造难度 | 判断 |
|---|---|---|---|
| **渲染器** | `gl_compatibility` | 中 | ⚠ 必须切 `forward_plus`（GL 兼容模式无 DOF / Bloom / SSAO）。但项目**自定义 shader = 0 个**，不用重写任何着色器，风险远低于常规项目 |
| **逻辑层** | 357 处 `Vector2`，12 个场景 | **低** | ✅ `(x, y)` 直接映射成 `(x, 0, y)`，向量数学、点积、扇形判定全部不用改 |
| **视觉层** | `SkinVisual` 抽象 + `ArtDB` 集中表 | **低** | ✅ 全项目**只有 3 个文件**碰 `Sprite2D`。换 `Sprite3D` 只需在 `SkinVisual` 内加一个分支，玩法代码一行不动 |
| **UI 层** | 9 个文件用 `CanvasLayer`，面板 2588 行（占全部代码 17%） | **零** | ✅ CanvasLayer 不吃 3D 变换，**完全不受影响** |
| **物理** | 4 个 `CharacterBody2D` + 6 个 `Area2D` | 中低 | ✅ 推荐保留 2D 物理做判定、只把显示搬进 3D；若要真 3D 碰撞则需重写（不推荐） |
| **场景内容** | 12 个场景，地面都是 `ColorRect` | 中 | 3D 地形/建筑要全新建，但**目前一个成品都没有，不存在返工** |
| **美术资产** | 全色块占位 | **高（真正的成本）** | 3D 场景建模 + 2D 立绘重绘。这部分工作量取决于质量标准，通常**远超代码** |

**综合**：代码侧属于「中等规模重构」，**不是重写**。真正的风险与成本在美术，以及下面第四节的设计矛盾。

## 二、为什么说现在是改造的最佳时机（甚至可能是唯一好时机）

这一点比技术评估更重要：

1. **美术零投入**。现在全部是 `ColorRect` 占位。一旦你按 2D 规格画好立绘/场景，改造就要**全部重画**——2D 精灵无法直接当 billboard 用，需要按「有立体感、能被光照」重新设计。现在改，浪费为零。
2. **0 个自定义 shader**。切渲染器最大的坑是着色器不兼容。本项目刀光、伤害数字、UI 全部用纯节点实现，切 `forward_plus` 几乎无险。
3. **`SkinVisual` 抽象层已存在**。这是当初「美术可替换性」约定的直接红利——所有角色形象都从这一个节点产出，换实现不动调用方。
4. **场景只有 12 个**。重建成本可控；如果后期铺到 50 个场景再改，代价是现在的 4 倍以上。
5. **UI 占比 17% 且完全免疫**。面板、背包、功法库这些「看不见的工程量」全部保留。

## 三、三条路径对比

| | **A. 伪 HD-2D** | **B. 立体 HD-2D（推荐）** | **C. 全面 3D 化** |
|---|---|---|---|
| 做法 | 保持 2D，用后处理 shader 模拟景深/光晕/移轴 + 多层视差 | 逻辑仍 2D 平面，渲染层换 3D；`(x,y)→(x,0,y)` | 坐标、物理、判定全部 3D 化 |
| 代码量 | 小（1~2 周） | 中（3~4 周） | 等于重写（2~3 个月） |
| 视觉效果 | 「有电影感的 2D」，**没有立体感** | 真正的八方旅人质感 | 全 3D，但会丢掉 2D 动作的精准手感 |
| 战斗影响 | 无 | **需解决视角与判定的偏差**（见第四节） | 手感全部重调 |
| 美术成本 | 低（继续 2D） | 高（3D 场景 + 立绘） | 极高 |
| 推荐度 | 预算/周期紧张时的降级方案 | ★ **推荐** | ✗ 不建议 |

## 四、必须先解决的设计矛盾：即时战斗 × 斜视角

这是整份分析里最需要你注意的一点，**它不是技术问题，是设计问题，且无法靠写代码绕开**。

八方旅人是**回合制**：玩家不需要精确走位，斜俯视角 + 景深只服务氛围，看不准也没关系。
本项目是**即时战斗**：弹刀窗口 0.22s、必须站定、完美弹反还带定身与追击位移 —— **全部依赖玩家对距离和朝向的精确判断**。

切到 HD-2D 的斜视角后会出现三个具体问题：

1. **透视误差**：屏幕上看到的「它离我 100px」和逻辑上的 100px 不是一回事。斜视角度越大，误差越大。
2. **景深干扰**：HD-2D 的标志性移轴景深会把远离焦平面的东西糊掉——但战斗恰恰需要看清边缘的敌人。
3. **立绘朝向**：billboard 角色没有转身中间帧，敌人「面朝哪」在斜视角下更难判断，而弹刀需要判断对方是否在攻击你。

**可行的解法（必须二选一）**
- **正交相机 + 固定俯角**（约 30°）：彻底消除透视误差，视觉与判定一致。代价是失去一部分「景深电影感」，但仍是明确的 HD-2D 观感。**推荐。**
- **透视相机 + 地面指示器**：保留景深，用地面网格、攻击范围描边、锁定标记来补偿。观感最好，但要额外做一整套战斗指示 UI。

## 五、推荐路径（B）的实施阶段

| 阶段 | 内容 | 产出 | 预估 |
|---|---|---|---|
| **0. 渲染器切换** | `gl_compatibility → forward_plus`；全场景回归测试（UI 混合、2D 光照、性能） | 现有游戏在新渲染器下正常跑 | 2~3 天 |
| **1. 坐标桥 + 角色 3D 化** | 逻辑层不动；加 `Visual3D` 桥接，每帧把 `Vector2` 同步到 `Vector3(x,0,y)`；`SkinVisual` 加 `Sprite3D` 分支 | 角色站在 3D 空间里，判定与现在完全一致 | 约 1 周 |
| **2. 场景 + 光照 + 阴影** | 地面换 `PlaneMesh`；`DirectionalLight3D`；角色加贴地假阴影（HD-2D 立体感的关键） | 主城与战斗场景的立体观感 | 约 1 周 |
| **3. 相机与后处理** | `Camera3D` 正交 + 固定俯角 + 跟焦；环境设置开 Bloom / 色调映射 / 轻景深 | HD-2D 成片观感 | 3~5 天 |
| **4. 美术替换** | 按 `art_db.gd` 条目逐个填 3D 模型与立绘 | 正式画面 | 取决于质量标准 |

**代码侧合计约 3~4 周**（不含美术）。

### 已知技术坑（提前记下来）

1. **`Sprite3D` 的 billboard 模式下不能用 `scale.x = -1` 翻朝向**——会镜像整个变换导致 billboard 失效。必须改用 `flip_h`。而项目现在是**由调用方**翻转：`player.gd:1434` 与 `primordial_player.gd:92` 都是 `anim.scale.x = ±1.0`。
2. **透明排序**：`Sprite3D` 要设 `alpha_cut = ALPHA_CUT_DISCARD`，否则多个半透明角色互相穿插。`no_depth_test` 绝对不能开。
3. **`y_sort_enabled` 失效**：2D 靠 Y 轴排序决定前后遮挡，3D 靠深度缓冲。若角色一半透明，排序问题会很顽固。
4. **`CanvasLayer` 下的 3D 节点不生效**：现有 9 个 UI 文件是 CanvasLayer，它们要显示 3D 内容的话需要 `SubViewport`，不过本项目 UI 全是纯 2D 控件，**不需要改**。
5. **`Area2D` 与 3D 视觉的位置漂移**：判定用 2D 坐标、显示用 3D 坐标，两套坐标必须在同一帧内同步，否则会出现「打中了但没显示命中」。

## 六、需要你拍板的三件事

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | 你要的是**立体 HD-2D（A）**还是**高清 2D（B）** | 成本差 5 倍以上。若是 B，现在就能做，只换 `art_db` 素材 |
| 2 | 战斗视角能否接受**正交相机 + 固定俯角** | 这是保证「视觉 = 判定」的唯一低成本方案；不接受就要额外做一整套地面指示 UI |
| 3 | 美术从哪来（自己建模 / 买素材包 / 外包） | 决定这个项目是否真能落地。代码 3~4 周就能改完，但美术是无底洞 |

## 七、一句话总结

**改，现在就该改；而且改的只是「怎么画」，不是「怎么玩」。**

架构上你已经占了三个便宜：`SkinVisual` 单点出图、`ArtDB` 集中登记、`0` 个自定义 shader。
真正的门槛不在 Godot，而在两件事——**你愿不愿意接受固定俯角**，以及**3D 场景美术谁来产出**。

如果这两个问题解决不了，退到路径 A（纯 2D + 后处理美化）依然能让画面质感上一个台阶，且完全不碰现有架构。
