# 卡片召唤自走棋 · 设计案（2026-11-02）

> 第四套玩法循环。对手先做**单人 vs AI**，但架构必须为以后的真人联机留门。
> 决策全部来自 2026-11-02 的逐题访谈，共 8 条，见下表。

## 1. 规则

1. **选牌**：双方各选 **6 张** BOSS 卡，来自**自己的卡包**（已解锁的牌）。
2. **锁定**：各自指定 **1 张锁反面、1 张锁正面**；剩下 4 张由系统随机 **2 反 2 正**。
   合计每人 3 正 3 反。此阶段对手看不见。
3. **布阵**：棋盘 **6 排 × 6 格**。双方**轮流各放 1 张**，朝向由锁定结果决定；
   正面朝上的落子对手能看见是哪只 BOSS。放满 12 张为止。
4. **对战**：每轮双方**同时暗选**一张卡激活 —— 奇数轮选**己方**、偶数轮选**对方**，
   交替进行。两边都提交（或选牌窗口到点）后**同时召唤**，打 **15 秒**，再进下一轮。
   **选牌期间场上棋子时停。**
5. **胜负**：12 张全部翻完后不再放新子，**清场制** —— 场上只剩一方有活棋子则该方胜。
   翻完之前**不判负**。从翻完起最多再打 **120 秒**；**第 60 秒起全场时间流速线性推到 2.0 倍**。
   超时则比**剩余血量百分比之和**（不比绝对值，否则上限高的天然多一条命）。

### 为什么激活敌方卡是成立的

12 张最终**全部要翻完**，所以"激活敌方卡"不是"要不要让它进场"，而是
**"它什么时候、在哪个格子进场"**。整局唯一的决策轴是**顺序 + 落点**。

数学上是闭合的：6 轮 × 双方 = 12 次激活；每队 3 次自己激活自己的（奇数轮）
+ 3 次被对手激活（偶数轮）= 6 张，正好翻完。而且己方回合候选集是己方的牌、
敌方回合候选集是对方的牌，**两边永远不可能选中同一张**。

## 2b. 入场与奖励（第二轮拍定 2026-11-02）

| 项 | 决定 |
|---|---|
| 入口门槛 | **没有门槛**，随时可进 |
| 卡池 | 自己的卡包（已解锁的牌），**含四位大陆核心首领**，共 16 位 |
| 不足 6 张 | **随机补满**（保留已有的，只补差额）；不是按固定顺序发凡界那几只 |
| 奖励 | **晶石**，押注制 |
| 保底位 | **作废** —— 那个概念只在轮抽方案里成立，本模式是自选 6 张，没有"被抢走"问题 |

### 押注规则

胜者拿走双方注额，但**有效注额按两人中较少的一方计**，多押部分原样退回：

```
有效注额 = min(A押, B押)
A 赢 → A +min、B −min；各自超出 min 的部分退回本人
```

零和：谁都不会因为押得多被多扣，系统也不凭空印钱。
例：A 押 100、B 押 50 → 有效 50。A 赢则 A +50（并退回自己多押的 50）、B −50。

**对 AI 时让 AI 镜像玩家的注**，所以 `min` 恒等于玩家自己的注、收益完全由玩家控制风险；
`min()` 这条规则本身是留给以后真人对局的。

注额区间 `BET_MIN = 50`（与卡包「非普通卡每张领 50 晶石」同档）～ `BET_MAX = 5000`，
必须不超过钱包。

## 2c. 关卡制（2026-11-05 逐题访谈拍定）

**本节取代 §2b 的奖励口径。** 押注制作废，棋坛改成一条无限延伸的关卡阶梯。
两条不可逆决策分别记在 [ADR-0001](adr/0001-棋坛关卡制取代押注经济.md)
与 [ADR-0002](adr/0002-关卡卡组由关卡号确定性生成.md)，术语见仓库根 `CONTEXT.md`。

| 项 | 决定 | 为什么 |
|---|---|---|
| 骨架 | **无限关、线性推进**：只能打「当前关」，已通关的可回去重打 | 关卡号当种子才能无限生成；线性才有"往前推"的进度感 |
| 奖励 | **首通一关 8 锻造晶石，只发那一次**；重打 / 输 / 平局一律 0 | 8 小到不能刷，无限关才不会变成无限印钱 |
| 押注 | **取消**（进关不扣钱、输了不罚） | 押注的前提是"玩家自己控风险"，和"同一副固定卡组可以零成本反复重试"直接打架 |
| 代价 | 弃局 / 战败**零代价**，不限次 | 关卡是解谜，重开成本必须是零 |
| 对手卡组 | **由关卡号算法实时生成**，不由人工设计 | 手写 3400 副组合既不可维护，也无法保证互不相同 |
| 固定性 | 同一关在任何存档、任何时候重打，对手**完全一致** | 这是"可以针对"的前提，否则固定卡组没有意义 |
| 卡池来源 | 从**全部 16 位**生成，**不读玩家解锁进度** | 一旦读解锁进度，玩家多开一只卡池就变，"固定"二字不成立 |
| 不重复 | **严格去重**：第 N 关必须与 1..N-1 每一副都不同 | 用户明确要求"每一关都不一样"；seed 直摇在 ~126 关就会生日碰撞 |
| 难度曲线 | 按**原始面板 HP×攻击的名次**加权抽卡 | 关卡号不参与任何数值计算，难度只来自"谁上场" |
| 数值 | **不膨胀**：`PIECE_HP_BASE / FACTORS / ATTACK_CALIB` 不因关卡乘任何系数 | 用户原话「数值不会膨胀」 |
| 预告 | 关卡界面**完全摊开**对手 6 张（身份可见，正/反仍保密） | 固定卡组只有在能被针对时才有价值 ⇒ 关卡是解谜不是遭遇战。⚠ 这条口径在 §2d 细化过一次 |
| 结算后 | 「返回」回**棋谱长卷**，不是回主城 | 一关接一关地推，不该每局都重新点一次设施 |
| 弃局 | 设置面板加一条「返回原初位面」，**只在棋局场景出现** | 给 BOSS 战开一个无代价逃跑键会白嫖塔层与赤霄界三强 |

### 界面母题：棋谱长卷

全屏舞台，一幅从左往右展开的水墨手卷。**每一关是卷上的一「局」**：一枚 6×6 棋盘拓印，
对手那 6 张卡**当作落子嵌在格子里**，不是旁边再列一排卡片清单 —— 信息本身就是装饰。
卷首竖排题签，卷尾留白；当前关之后 5 关可预览，更远的挂几枚"还没展开的纸轴"，
读作「卷还在往右长」。

### 落地时推翻的两处估算（都已在 ADR 里订正）

1. **可达组合不是 C(16,6)=8008，实测约 3400**：加权饱和（第 50 关起 bias=1）后强半区几乎垄断抽样，
   严格去重实际守到**约第 416 关**。玩家几百关已是极限，够用，但别再引用 8008 这个数。
2. **`MAX_REROLLS` 从 64 降到 12**：64 次把 1..8100 关的生成拉到 64 秒；
   真实区间占用率 <5%，连续 12 次撞车的概率约 10⁻¹⁶，去重照样成立。
   降下来后 1..300 关 56ms、冷启动单关 6ms。

### 2c-1. 实机第一轮之后的三条追加（同日，用户看完长卷与棋局后提）

| 追加 | 口径 | 为什么 |
|---|---|---|
| 长卷加「返回原初位面」 | 底栏 CTA 左侧一个 quiet 档按钮，点了直接回主城、不改进度、不弹确认 | 长卷是整屏场景不是面板，之前唯一的出口是"进关再弃局" —— 用户实机第一下就撞上了 |
| 敌方卡面固定**原版** | 新增 `MatchCard.opponent_style()`，覆盖长卷拓印落子、长卷底栏、对局棋盘 `team != 0` 的棋子 | 之前敌方也走 `cover_style(id, match_card_kind)`：读玩家偏好 + 读玩家解锁进度，对手 6 张水墨华彩混着来，还把进度写进对手外观 |
| 战斗两档缩放 | 常规档=选牌/锁定/布阵/结算（棋盘贴左+右侧手牌列）；**看盘档**=普通模式整个 BATTLE（手牌收掉、棋盘放大居中），相机 exp 插值 τ=0.12s | 用户原话「引导玩家这时是关注棋盘还是选择激活棋子」。**2026-11-10 改口径**：原来按 `round_index % 2` 判，六轮 480↔568 来回跳（面积差 39%），用户报「棋盘缩放有问题」；现在激活只点棋盘上的卡片、不需要给手牌让位，于是普通模式 BATTLE 一把恒定在放大档 |

⚠ **放大的上限是几何，不是没做够**：棋盘是 1560×1560 的正方形，横屏里 `min(宽/棋盘, 高/棋盘)`
绑死它的是**高度**。所以右侧手牌列占掉的那 800px 宽度本来就用不上，收掉面板本身不会让棋盘变大；
能拿回来的只有上下两条 HUD 带省出的那点高度 —— 1280×720 实测 `z 0.3077 → 0.3641`，
**线性 +18%、面积 +39%**。要更多就只能让 HUD 文字压到棋盘上，那是之前"文字堆在棋盘上"那条投诉的反面。

⚠ 看盘档只能 `visible = false` 收面板，**不能淡出**：`CardFace` 的图是 ShaderMaterial 画的
（`card_face.gd` 里 `face.material = _still_mat`），那条 shader 不乘 `COLOR`，
父节点 `modulate.a` 压到 0.01 卡面照样全不透明 —— 第一版就是这么"淡不掉"的。

### 2c-2. 2026-11-10 实机追加三条（用户「棋盘缩放有问题 / 补牌要普通卡面」）

| 追加 | 口径 | 为什么 |
|---|---|---|
| 普通模式 BATTLE 恒定放大 | `_camera_mode()` 只要 `not _quick and phase == BATTLE` 就返回看盘档（568px），六轮不再按 `round_index % 2` 切；快速模式 BATTLE 保持原判据 | 原来己方轮 480 / 对方轮 568 逐轮来回跳，用户报缩放有问题。激活改成只点棋盘上的卡片后，不需要再给手牌列让位 |
| 选卡聚光 | 每个「BATTLE 且 `not fighting()` 且 `legal_activate` 非空」的时停窗口：棋盘**底图**压暗（`PickDim`，绝对 z=-5）、不可选牌用 `self_modulate` 自己压暗、可选牌保持全亮 + 暖金呼吸灯。玩家已提交、等 AI 的半秒不压（否则整盘全黑却没亮点） | 用户要「整个棋盘变暗，只有可以选择的卡片变亮」。⚠ 遮罩绝不能盖到卡片上：第一版用「遮罩 z=8 盖全部 + 可选牌提到 z=9 穿透」，实机染红诊断显示 92% 棋盘连可选牌一起被盖住（Godot 子节点绝对 z 争不过父 `_tokens` 分组）。卡片压暗走 `self_modulate` 而不是 `modulate`，避开 `set_dim()` 那条 alpha 通道 |
| 开局补牌 = 普通卡 | 新增 `MatchCard.player_style()`：`ordered_variants` 为空（= `!is_boss_unlocked`，正是 `fill_pool` 补的那一批）就走 `portrait_style()`；已收集的仍走 `cover_style()`。手牌 / 拖影 / 结算 / 棋盘 team=0 四处统一 | 用户报「不足 6 张时补的牌是华彩」。根因：`cover_style` 在 owned 为空时退回全量 `card_variants`，第一张恰好是「华彩·有背景」（codex_db 注明「默认封面，排第一」）。敌方 2026-11-05 已用 `opponent_style` 绕开，玩家补牌是同一根因的另一半。⚠ 不改 `cover_style` 本身，卡包收藏册口径不变 |

验收：`probe_match_cards` **68/0**（⑥c 组 15 条 + 整局结算页逐张验「6 张 / 华彩 0」）、
`probe_match_level_all` **52/0**、`probe_match_quick_camera` **17/0**（档位表 + 全视口几何）、
`probe_match_clicks` **31/0**（窗口模式）。四个变异测试都验过能红：
改回按轮次切相机 → 2 红 + 1 红；`player_style` 改回 `cover_style` → 4 红；
去掉可选牌明暗通道 → 1 红；只把结算页一处改回 `cover_style` → 2 红（结算页实测 6 张全华彩）。


## 2d. 快速模式（2026-11-05 第二轮逐题拷问拍定）

普通模式那套「选牌 → 定正反 → 双方交替布阵 → 六轮逐张翻牌」里，真正花时间的不是战斗，
是**六轮每次只翻一张**的决策循环。快速模式就是把这段压掉：进关即见对方 6 张已摆好，
玩家只摆自己 6 张，点「开战」→ 12 只同时上场 → 等一个结果。

| 决策 | 口径 | 理由 / 被否的备选 |
|---|---|---|
| 定位 | **与普通模式完全等价**：同样 +8 首通晶石、同样推进最高关、同样可重打 | 8 晶石本就极小（ADR-0001），再分一档收益只是多一套规则要守。"给钱但不推进度"被否：长卷进度与剪影分界会多出一种解释 |
| 代码分离 | 同一个 `MatchState` 加 `quick` 开关，三个分叉点各封成独立函数，普通路径一行不改 | 子类被否（`Phase` 枚举/事件字典/类型判断到处是，改动更大）；独立场景被否（HUD/结算/卡面/相机要复制或抽基类，正是"搞混"的反面）。见 ADR-0003 |
| 对方摆位 | **按关卡号派生种子 ⇒ 同一关布局永久固定，可背板**；普通模式仍每次随机 | 只固定快速模式，不两种都固定：后者要重跑 39 项数值模拟并不可逆地改掉现有手感。见 ADR-0004 |
| 玩家正反面 | **6 张全正面**（跳过 LOCK 那一步） | 备选"也自动三正三反"（与普通模式 LOCK 结果同分布）被用户否。后果：快速模式没有"反面按就近落位"这一层 |
| 终局时间窗 | **240s**，加速曲线按窗口等比重算（120s 起推、240s 到 2.0×） | 推导口径 = 同一份战斗预算：普通模式最多 6×15=90s 轮次 + 120s 终局 = 210s。普通模式的 120/60 一个数字不动 |
| 相机 | **新增第三档**：常规 480px / 看盘 568px / **快速 616px**（1280×720 实测） | 快速模式没有"轮到对方"那一下，两档相机的触发条件永不成立，终局 240 秒面板会白杵着。第三档把上下带压到 34/34+overhang 18，倒计时搬到顶带右侧（几何天花板 0.4615，616px 已用到 86%） |
| 开战按钮 | 6 张没摆完禁用并显示「还差 N 张」；「跳过（按策略代打）」保留 | "摆完自动开战"被否（没有环视机会，且与"再点击开战"相左）；"始终可点、漏的自动补位"被否（玩家会误以为摆好了） |
| 开关 | 长卷底栏 quiet 档，**入存档** `match_quick_mode`，默认**关**，长卷与结算页处处标注 | 不入存档被否（每次都要重开＝bug 感）；不标注被否（等价 ⇒ 玩家可能忘了自己开着快速，打完才发现没做过逐轮决策） |
| 拓印 | 快速模式下画**真实落位**，反面那 3 格画**牌背** | 备选"压暗画卡面"被否。由此把「完全预告」细化为：**6 张身份全摊开，但反面卡的格子对应关系不摊开**。⚠ 普通模式那一侧已在 §2g 改版为**不画格子** |

### 口径细化：预告

§2c 那条「身份可见，正/反仍保密」在快速模式下不够用了。现在的口径分两层，
`CONTEXT.md` 的「预告」「拓印」两条已同步改写：

- **卡组身份**：任何模式下 6 张全摊开（拓印画一遍、宽屏时底栏那排小卡再复读一遍）。
- **格子对应关系**：普通模式是展示约定（拓印落点是装饰）；快速模式按关卡号固定，
  所以拓印画真实落位——但反面那 3 格只画牌背，"这一格有张反面的牌"公开，
  "它是哪一只"仍要进关才知道。

⚠ 硬约束：**拓印用的布局函数必须就是对局开局真正摆位的那个函数**
（`MatchQuickSetup.layout_for(level)`）。两处各算一次就会漂移，

```
1920×1080 → 840 / 928 / 976 px
1280× 720 → 480 / 568 / 616 px     ← 票 005 定档的那一档
1024× 600 → 360 / 448 / 496 px
 800× 480 → 240 / 328 / 376 px
 740× 360 → 160 / 208 / 256 px
```

排序会不会翻立刻看得出来。

## 2f. 同场共存：棋局是全项目唯一的"两只 BOSS 同场"（2026-11-05）

用户实机棋局崩死，报 `Invalid access to property or key 'source' on a base object of type 'Node2D (ArrayFlag)'`，
每帧 116 条。修完做了一次同族审计，结论是：**崩溃只是这类问题里唯一会喊出来的那一个。**

### 为什么单打永远测不出来

`match_adapter.gd` 把真 BOSS 场景同时挂进一棵树（最多 12 只），这是全项目唯一的多 BOSS 环境；
而且玩家 6 张与对手 6 张各自生成，**可以出现同一只 BOSS 的两个实例**。于是两类假设在这里第一次失效：

1. **组同质**：`breakable_sword` 是异构组（剑客天剑 / 定阵先生阵旗 / 石犼碣板都进），
   只有 `SkySword` 有 `source` 与 `dismiss()`。剑客直接读字段 ⇒ 一插旗就崩。
   玩家侧读同一个组的两处一直用 `has_method("take_hit")` 筛，是守约的；违约的是剑客自己。
2. **阵营等于组名**：主路径 `enemy_units()` 早按 `team_id` 走 `match_piece`，是对的；
   但**卫星实体不是 BossBase**，用不了实例方法，于是各自按 `"player"` / `"boss"` 字符串拼阵营。
   棋局里没有 `"player"` 组节点 ⇒ 列表恒空 ⇒ **机制静默 0 效果，不崩、不报错、探针也不红**。

### 统一入口

`BossBase.hostile_units(source)` / `hostile_target(source)`（静态）。口径与 `enemy_units()` 一致，
只是不要求调用者是 BossBase：棋子按队伍、BossBase 复用自身、玩家侧扫 `boss` 组。
**没有队伍号时行为一字不变** —— 这就是每条探针都配一条反向判据的原因。

改掉的 8 处（六条 `probe_*_match` 共 72 项判据）：

| 卫星 | 原写法 | 棋局里的真实后果 |
|---|---|---|
| 剑客 `_remaining_sky_swords` / `_settle_sky_swords` | 直接读 `sw.source` | **崩溃**（每帧刷） |
| 刀痕 `blade_scar` | 按 `"player"` 组取敌 | 刀客招牌伤害**一刀不劈**；且伤害签名会塞错参数 |
| 禁步桩 `treasure_stake_field` | `"boss"` 组 + `is_ally` 反筛 | 12 只全是非友军 ⇒ **谁也圈不住** |
| 蚀甲锥 `treasure_cone` | 固定 `target_group="player"` | **恒不命中** |
| 天火种 `_find_seed` | 返回组里第一颗，不看归属 | 后落的离照不补种、把别人的火当自己的、被别人的「火种被夺」白送一次出手 |
| 镜身 `mirror_image` | 查 `"player"` 组；无 `team_id`、不入 `match_piece` | 镜像**既不出伤也不走位**，且**打不碎**会堆积 |
| 界灯 `shadow_lamp` | `find()` 返回第一盏，无归属字段 | 第二只执烛在别人那盏下跑全套减益 |
| 分影 / 镜环场 | 按 `faction` 扫 `player`/`ally_summon` | 目标列表恒空 |

### 三条没照着审计报告改（都是报告里看着像 bug 的）

- **刀痕上限 `MAX_NORMAL=4` 双方共用**：`scar_field.gd` 头部写明是设计
  （"双方共用同一份实例与上限，玩家学会刀客招式后能和 BOSS 打同一套刀痕博弈"）。不改。
- **定阵先生的阵域**：审计报成"按 player 组定阵营 ⇒ 棋局空转"。读代码后不成立 ——
  `_zone_units_inside()` 走的是 `attack_units()`（队伍感知），
  `_set_zone_unit_debuff()` 的 `elif has_method("set_zone_attack_mult")` 正好接住棋子。本来就好的。
  **审计报告要逐条验，不能当清单执行。**
- **界灯的"同场只有一盏"**：`_ensure_lamp()` 注释写明是设计（召唤执烛助战时复用敌方那盏）。
  所以只在发起者**带队伍号**时才按队伍筛，单打复用一字不变。

### 追问时新发现的第九条：石犼「闻声」——拍定为单打专属

回答"都修好了吗"时重扫了一遍全项目 `player` 组查询（18 处），
发现审计与第一轮都漏了这条，因为它不写字面组名，藏在 `_find_prey()` 里：

```gdscript
func _find_prey() -> Node2D:
    return get_tree().get_first_node_in_group("player") as Node2D
```

棋局里没有玩家节点 ⇒ `_prey` 恒 null ⇒ `_tick_noise()` 与 `_echo_pulse()` 都在第一行返回：
声追踪、P2 回声的「被听见了」、`shihou_pounce` 冷却重置全不触发。

**2026-11-05 用户拍定：定为单打专属，不改代码。**
理由是噪声源本身是玩家专属遥测（`noise_ping_seq` / `noise_ping_pos` / 闪避 / 结符），
而"安静站着就不被听见"这套博弈的前提是场上有个在控制动静的人；
对面换成 12 只 AI 时，这条机制对玩家没有意义 —— 硬映射到棋子身上只会造出一段
"说不出为什么"的强度变化。

`tools/probe_shihou_scope.tscn`（10 项）把这条从"静默坏掉"变成"验证过的范围限制"：
① 限制确实成立且空跑不报错；② 石犼在棋局里**仍是会打的正常棋子**
（目标解析、`focus_node`、攻击力折算都验过）；③ 单打的声追踪照旧认玩家（限制没被反向扩大）。

⚠ 这条探针顺带定下一条**夹具规矩**：凡是被生产代码用 `bool(...)` / `float(...)` 包住
`get()` 读过的字段，桩节点一律不许裸造 —— 裸 `Node2D` 桩没有 `is_dead`，
`bool(null)` 在本机直接报 "Nonexistent 'bool' constructor" 并每帧刷屏。
本次开发连着踩了三次（`probe_treasure_match`、`probe_shadow_match`、`probe_shihou_scope`），
要么用真场景，要么先 grep 出被读的字段再补。

## 2g. 普通模式拓印改版：不画格子（2026-11-05 用户拍定）

用户实机问「为什么选择关卡界面看不见对手的布阵」。查下来答案是两层。

**第一层是设计口径**：普通模式的真实布阵在进关之前**根本不存在** ——
格子与朝向是开局那一刻用本局随机种子现摇的（ADR-0004 拍定「只固定快速模式」）。
所以长卷上不可能画出真阵型。

**第二层是界面失职**：`_rebuild_focus_reading()` 只在快速模式加了一句
「阵型已固定 · 拓印即真实落位」，普通模式**什么也没说**。
于是 6 张牌明明白白嵌在 6×6 格子里、画得跟真阵型一模一样，玩家自然读成"这就是我要打的阵"。
整块板只有一层表示"朝向未知"的面纱，**位置的可信度从没被质疑过**。

拍定的修法不是补一句文案，而是**把误导的源头去掉**：

| | 普通模式 | 快速模式 |
|---|---|---|
| 6×6 网格 | **不画**（`Rubbing.grid = false`） | 画 |
| 6 张卡 | 方块内 **3 列 × 2 行** 卡组清单 | 嵌进**真实落位**格子 |
| 反面 | 面纱（朝向进关才定） | 逐张画**牌背** |
| 读数 | 「阵眼 · X　当前局 · 可挑战」 | 追加「阵型已固定 · 拓印即真实落位」 |

**为什么是 3×2 而不是"一列 6 张"**：方块边长 340 时一列只剩 37px 宽，卡面糊成一团；
3×2 每张约 80×121，卡面与名字都还读得清。清单尺寸全部由方块边长推出来
（`LIST_PAD = 0.10` / `LIST_GAP = 0.045`），所以换窗口、换 `TILE_MIN/MAX`
都不用回来改数字；而且 footprint 与原来完全一致 ——
长卷的横向节奏、题签位置、朱砂印角、卷边一个都没动。

**为什么"不画格子"比"补文案"好**：文案要求玩家读到并理解一层模式差异；
没有格子则一眼就不可能误读。这条口径本来就有先例 ——
剪影关画成"还没展开的一截纸轴"而不是"空拓片 + 一行说明"，同一个道理。

判据：`probe_match_quick_rubbing` ④ 从"落点仍是 STONE_CELLS 装饰格"整段换成
清单形态判据（`grid == false`、6 张不缺、全在方块内、互不重叠、每张 ≥60px 宽），22 → 26 项。
快速模式那一侧的 ①②③⑤⑥ 一条没改，仍验真落位与牌背。

⚠ 这次改版**推翻了票 006 的拓印形态**（当时定的是"6 张作为落子嵌在格子里，
不是旁边的卡片清单"）。那个理由在快速模式下依然成立，所以那句话现在只对快速模式成立 ——
CONTEXT.md「拓印」条已按模式改写。

## 3. 代码结构

```
scripts/match/
  match_db.gd        规则常量 + 真实面板快照 + 折算系数 + 校准表
  match_state.gd     状态机。一切推进只走 apply_command(cmd)
  match_policy.gd    decide()：AI 与超时代选共用
  match_combat.gd    抽象战斗模型（只用于规则层模拟，第 4 步起被真棋子替换）
  match_adapter.gd   生成真 BOSS 棋子：队伍号 / 折算面板 / 战场边界 / 不按时消散
```

### 联机接缝（硬约束，不是愿望）

- 所有决策必须是**普通字典命令**，不能"当前帧读本地输入"。
- 所有随机只走 `state.rng`（吃本局种子）。洗牌自己实现了 Fisher–Yates ——
  `Array.shuffle()` 走引擎全局随机，两个客户端拿到同一串命令会洗出不同正反面。
- 补发牌必须是**确定性**的：同样的解锁状态 → 同样的结果，否则服务器还得额外同步这笔随机数。

## 4. 两条不能凭感觉定的数

### 棋盘格子边长 = 260px

`BossBase.PHASE_TRANSITION_PUSH = 520`（转阶段击退）。按每格 160px 算，棋盘 960×960、
半宽只有 480 —— **一次转阶段击退就超过半宽**，棋子会被钉在墙上反复弹。
6 × 260 = 1560，半宽 780 > 520 + 48（`combat_arena.gd:1766` 的钳制是 `half - 48`）。

### 真实 DPS 必须逐只实测

`attack_power` 直接当 DPS 用是错的。实测 `atk = 100` 时真实输出只有 **4–40 DPS**，
即高估 **10–200 倍**；而且逐只差到 **13 倍**（气君需 atk 2073，虎妖需 26579 才打到同一档目标）。
原因：招式伤害 = attack_power × 系数，但一只 BOSS 在一段时间里**实际出手几次**
取决于它的 AI 节奏 —— 前摇、走位、召镜像、放领域、二阶段演出全在吃时间。

实测结果落在 `MatchDB.ATTACK_CALIB`，`MatchAdapter` 用它设 `attack_power`；
缺值时退回目标 DPS 并 `push_warning`（宁可吵，也不要静默造出一只几十倍弱的棋子），
`probe_match_rules` 另有硬断言「16 位全部有校准值」。

⚠ **10 秒测量窗口有噪声**：苍角两次跑出 20 / 14 DPS（差约 45%）。定稿前要用更长窗口复测。

### 四位核心不是 BossBase 场景，是 WorldEnemy

`secret_world.gd:884 _spawn_core()` 走 `WorldEnemy.configure(cfg, KIND_CORE, name)`，
招式来自 `SecretWorldDB.CORE_SKILLS`。若按 `WorldDB.get_boss_scene()` 装配，
核心查不到登记会**静默回退**到 `boss.tscn`（通用 `prototype_boss`，
没有 `boss_id` 属性、没有数据驱动招式）—— 四只变成同一套假招式，一行错误都不报。

两个连带坑：`configure()` 会**覆写** `max_hp`/`attack_power`（折算必须排在它之后）；
它把 `spawn_home` 设成该核心在大世界的坐标（搬到棋盘不改就是几千像素外，
棋子会一边打一边被脱战逻辑拽走）。

还有一层：`WorldEnemy._tick_threat` 是大世界的「进战半径 + 脱战回家」覆写，
没有玩家时每帧把 `target` 清成 null；而**石犼又自己覆写了 `_tick_threat`**（闻声机制），
父类的修复到不了它，得两级都加 `team_id >= 0` 分支。
判据在 `probe_match_pieces._check_cores_are_world_enemy`（身份 + 招式表 + boss_id + spawn_home）。

## 6d. 棋盘放大到整屏（2026-11-03 用户：「放大棋盘到整个屏幕，但不要超过屏幕」）

### 上限怎么算

棋盘是 **1560×1560 的正方形**，横屏里由**高度**封顶：
`zoom = min(视口宽/1560, 视口高/1560)`。1280×720 → `z = 720/1560 = 0.4615`，
棋盘屏上 **720×720**（原来只有 424×424，大了 2.7 倍面积）。
按宽度放会把上下两排推出屏幕，所以"不超过屏幕"就是一道 min。

### 关键一步：HUD 不能再从棋盘身上切带子

上一版为了不让手牌条压住棋盘，把「顶部信息高 + 底部手牌高」从视口里扣掉再算缩放 ——
那等于**让 HUD 吃掉棋盘**，玩家看到的就是"中间一小块棋盘、两侧各空 280px"。
放大到整屏必须换思路：**棋盘贴左、HUD 让到右侧那条空白里**。

- `_fit_camera()` 算出 `board_w` 后，把相机 `position.x` 设成
  `(视口宽/2 − GUTTER)/zoom − 半宽`，棋盘左边缘就钉在屏幕 10px 处；
- 右侧剩下的 528px 交给手牌面板，`_layout_hand()` 用**屏幕像素 offset** 摆它
  （HUD 根节点因此必须是普通 `Control` 而不是 `VBoxContainer` —— Container 会接管并
  覆写每个子节点的矩形，手动摆位会被冲掉）；
- 列数按「每列至少 150 宽」往上加（1280 屏 → 3 列 × 162 宽，一屏看得见 8～9 张卡面），
  卡面尺寸 `_card_w` 由布局算、`_add_card_button` 读，不再写死 115；
- 视口太窄、右侧放不下手牌列时（接近 4:3 或竖屏）自动退回底部横条，
  并且**容器一律 `MOUSE_FILTER_IGNORE`** —— 横条压在最下排上，不穿透就点不到那 6 个格子。
  `IGNORE` 只挡自己不挡子节点，卡面按钮与滚动条照旧收点击。

### ⚠ `Node2D.get_viewport_rect()` 不是屏幕尺寸

`_fit_camera()` 原先写的是 `get_viewport_rect().size`，而本节点是 **Node2D**：
这个 API 返回的是「视口矩形在该节点局部坐标系里的大小」= **屏幕尺寸 ÷ 当前相机缩放**。
拿它去算缩放就是自我循环，实机表现为棋盘莫名又小一圈（该得 0.27 只算出 0.21）。
要真实像素只能 `get_viewport().get_visible_rect().size`（`Control` 上的同名 API 没这个坑）。
探针判据也必须走同一个口径，否则会假绿。

`probe_match_entry` 加了两条比例断言（只断比例，headless 下视口不是实机尺寸）：
「棋盘四边都不出屏幕」+「已放到不越界的上限（没留空边）」，外加两条手牌容器点击穿透。
截图 `output/match_ui_*.png` 六阶段全部重拍。

## 6e. 布阵点不动：整屏浮层的 mouse_filter（2026-11-03 用户报「布阵时选不了牌也点不了格子」）

### 先补上一直没人守的那一层

规则层探针喂 `apply_command()`，入口探针只验"阶段跑到了"，**鼠标能不能真的落到控件/格子上
从来没人测过**。所以 HUD 改成整屏浮层之后，一个 filter 设错就让选牌和落子同时死掉，
而五个探针全绿。新增 `tools/probe_match_clicks.tscn`：合成真实鼠标事件走一遍
点卡面 → 确认 → 锁反面 → 锁正面 → 点手牌 → 点格子，15 项。

⚠ **这条探针必须窗口化跑**：无头模式下 Viewport 根本不给 GUI 派发合成鼠标事件
（三种 filter 全部"按钮收不到、世界收得到"，会把结论彻底带偏）。
`godot --path . --resolution 1280x720 res://tools/probe_match_clicks.tscn -- --no-save`

### mouse_filter 真值表（实测，`tools/diag_gui_filter.tscn`）

浮层盖住整屏时，"浮层里的按钮"和"浮层空处底下的世界"各自能不能收到点击：

| 浮层 filter | 子按钮 | 空处→世界 | 结论 |
|---|---|---|---|
| `STOP`（裸 Control 的默认值） | 收到 | **收不到** | 棋盘格子全部点不动 |
| `PASS` | 收到 | 收到 | ✅ 唯一可用 |
| `IGNORE` | 收到 | 收到 | 也能用（IGNORE 并**不会**屏蔽子树） |

两条以前记错的直觉被这次实测纠正了：
① 子节点永远比父节点先命中，所以父节点 STOP **不会**挡住自己的按钮，它挡的是**世界**；
② `Viewport._find_control` 遇到 IGNORE **不会**整棵子树跳过，按钮照样收得到。
所以真正的凶手只有一个：**HUD 根节点从 `VBoxContainer`（Container 默认 PASS）
换成裸 `Control`（默认 STOP）之后，整屏把 `_unhandled_input` 饿死了。**

### 第二个真 bug：换阶段会抹掉玩家刚选中的牌

`_refresh_stage()` 以前在每次重建手牌的开头都无脑 `_sel_boss = ""` / `_sel_card = -1`，
而 `phase` **事件**比 `st.phase` **字段**晚到一帧（`_process` 先减表判超时，`_drain()` 才处理事件）。
玩家手快，就会在"点了牌 → 迟到的换阶段刷新把选择抹掉 → 点格子没反应"这条缝里踩空。
改成只在 `phase` 真的变化时才清，`_drain()` 的 phase 分支里那句重复清理一并删掉。
两条都有负测：把 filter 改回 STOP → 2 项红；把清理改回无条件 → 2 项红。

### 探针自己的两个坑（记下来，别再把产品判错）

- `_wait_phase()` 不能一到目标阶段就返回：`st.phase` 先变、手牌晚一帧才重建，
  中间取到的是**上一阶段的旧按钮**（它的回调写的是 `_sel_boss`），
  于是 `sel_card` 永远 -1，看着像产品的 bug。多等 4 帧再断言。
- 双方都提交完规则层才换阶段，而 AI 有 `AI_ACT_DELAY=0.55s`，点完立刻断言必然早。

`_is_sel_card()` 会把两张一起提亮。改成**按卡下标 `_sel_card` 选**，顺带和布阵共用一个字段。

## 6g. 节奏调整（2026-11-03 用户：选翻牌 10 秒、两次翻牌之间 15 秒）

只改两个常数：`MatchDB.PICK_SECONDS` 6→**10**（暗选窗口）、
`MatchDB.ROUND_SECONDS` 8→20→**15**（两次翻牌之间的战斗窗口，同一天先提到 20 再收到 15）。
全部计时都从这两个常数走，没有别处写死秒数。

一整局的时间预算因此变了：

| | 最初 (6/8) | 中间 (10/20) | **现在 (10/15)** |
|---|---|---|---|
| 一轮 | 14 秒 | 30 秒 | **25 秒** |
| 六个翻牌轮合计 | 84 秒 | 180 秒 | **150 秒** |
| 加上终局上限 | 204 秒 | 300 秒 | **270 秒** |

`FINAL_LIMIT_SECONDS`（120）与 `ACCEL_START_SECONDS`（60 → 线性推到 2.0x）按原设计不动 ——
用户当初定的就是"翻完后再打最多两分钟、后面一分钟开始加速"。

**顺带要改的两个工具**（不然它们会以为整局卡住了）：
`tools/shot_match_board.gd` 以前靠真实时间跑完整局，150 秒起它等不起，
现在在 BATTLE / FINAL 阶段把 `st.timer` 压到 0，让规则层走**它自己的**到点代选 / 收轮 / 终局判定路径
（不另写一套快进逻辑，测的还是同一段代码）；
`tools/probe_match_pieces.gd` 的 `duel_limit` 是独立参数（45 秒），不受影响。

**回归**：`probe_match_rules` 43→**48 项**，新增 5 条节奏断言 ——
既断常数，也断"进对战时 `timer` 真的按 10 秒起表""两张都提交后真的按 15 秒起表"
（常数对但被别处覆写，一样算跑偏）。千局模拟 `stall=0 max_steps=5215`（≈174 秒一局，
远低于 40000 步上限，说明拉长节奏没有把模拟逼到边界）。

### 棋子血量 ×3（同日，用户「都死太快了」）

只改 `PIECE_HP_BASE` 10000 → **30000**，`FACTORS` 一位都没动 ——
各只之间的相对肉度（观澜 1.18 / 叠纸 1.20 最肉，刀客 0.84 最薄）原样保留。
伤害侧（`PIECE_DPS_BASE`、`ATTACK_CALIB`）也没动，所以**单挑击杀时间直接 ×3**。

效果用一条性质钉住，而不是只记一个数：
**抽象模型里没有任何一对棋子能在一个战斗窗口（15 秒）内打死对方。**
最凶的一对是「刀客打刀客」：`30000×0.84 / (900×1.20)` = **23.3 秒** > 15 秒。
原来（10000 基准 / 8 秒窗口）同样是 7.8 秒 —— 连一轮都撑不满，那就是"死太快"的本体。
断言写在 `probe_match_rules._check_pacing()`，它遍历 16×16 全对取最快击杀，
所以以后无论改血量、改 DPS 还是改窗口长度，只要破坏"至少活过一轮"就会红。

配合 15 秒一轮，现在一只棋子要两三轮才倒得下 → 场上会明显攒得更满，
更多对局会打到终局阶段（120 秒 + 后 60 秒加速）才分胜负。

**真棋子实测**（`probe_match_pieces`，limit=45s）单挑击杀用时，同一批跑两次的数
（对决带随机性，**逐次会飘 5~10 秒**）：
观澜 vs 赫连霄 24.8 → **21.2s**、执烛 vs 气君 28.9 → **30.8s**、叠纸 vs 刀客 25.5 → **26.8s**、
苍角 vs 两仪 24.5 → **22.6s**、石犼 vs 定阵 16.0 → **26.1s**。
两轮里只有第一次的石犼那对（16.0s）贴着 15 秒窗口 —— 也就是说"活过一轮"在**真实模型里
是概率性的，不是每次都成立**。抽象模型的断言只管名义 DPS，抓不到这种抖动；
要真钉住得给 `probe_match_pieces` 加"每对连跑 N 次、取第 P 百分位的 TTK > 窗口"这种判据。

## 6h. 血条颜色显示错误（2026-11-03 用户报）

**根因是上色时机，不是配色表。** 队伍色只在 `BossBase._ready()` 里上一次色，
而 `WorldEnemy._setup()` 是被 `BossBase._ready()` 在**末尾**调用的钩子，
它里面按 `enemy_kind` 又把血条刷了一遍：

```gdscript
# world_enemy.gd _setup()
_hp_bar.color = _hp_color()      # KIND_CORE → (0.95,0.35,0.25) 橙红
```

于是**四只大陆核心棋子不管属于哪一队都顶着橙红条**，我方的也红；
12 只塔层 BOSS 没有这个后写，所以是对的。

**修法两处**：`_update_head_hp_bar()` 里重申队伍色（这函数被血量变化 / 布局 /
阶段切换各处反复调用，等于自愈，以后再有子类后写也压得住）；
`WorldEnemy._setup()` 刷完 kind 色后立刻补一次 `_tint_head_hp_bar()`，
让第一帧就是对的。`team_id < 0` 时 `_tint_head_hp_bar()` 直接返回，
所以大世界的野修蓝条 / 核心橙条原样不动，PvE 不受影响。

**为什么以前没测出来**：`probe_match_ranged` 只拿一只 `boss.tscn`（BossBase）验了颜色。
补的断言是 **16 位 × 两支队伍 = 32 次全覆盖**（`probe_match_pieces._check_hp_bar_colors`）。
负测：撤掉两处修复后恰好红 8 条 —— 四只核心 × 双方，全是
`(0.95,0.35,0.25) 应为 (0.32,0.82,0.42)`，12 只塔层 BOSS 一条没错，
正好对上"只有核心错"的现象。

**还剩一类同源的显示问题没修**：棋子自己召唤出来的单位（观澜倒影、石犼回声这类）
`team_id` 是 -1，血条走场景默认的红色 —— 自家棋子召出来的东西看着像敌方。
要修得让召唤物继承召唤者的队伍号，但召唤物是各 BOSS 脚本自己
`get_parent().add_child(...)` 出来的，`Pieces` 层认不出它的主人，
得先给每只棋子一个自己的 host 节点。属于逐招裁剪表那一档的活。

## 6i. 两个"还是有 bug"的实测结论（2026-11-03 用户带截图报）

### 每轮激活数量：不是规则层多给了，是**双方拿的是同一副卡组**

规则层实测每一轮都是 `0队=1 1队=1 → 2/2 → 3/3 → 4/4 → 5/5`，完全对称。
真正的原因在开局那一行：`_state.start([_pool, _pool.duplicate()], ...)` ——
**AI 的候选池就是玩家那一份的副本**，而两边又都走同一份
`MatchPolicy.decide_deck()`（按 DPS 取前 6）→ 两副卡组逐张相同。
进场日志里每个 boss_id **恰好出现两次、各在一队**：

```
+battle team=0 boss=boss_01     +battle team=1 boss=boss_01
+battle team=0 boss=boss_01_c   +battle team=1 boss=boss_01_c
+battle team=0 boss=boss_02_c   +battle team=1 boss=boss_02_c   …
```

于是每一轮双方放出的都是同一只，场上并排两只一模一样的 —— 玩家读成"一方激活了两只"。
**修法**：新增 `_ai_pool()`，优先取**玩家那张池子里没有的卡**（洗过、吃本局种子），
不够 6 张才复用。修完再测，两边卡组彻底错开：

```
team0: world_core_jiedan / boss_03 / world_core_lianqi / world_core_zhuji / boss_02 …
team1: boss_huyao / boss_02_c / boss_02_b / boss_04_b / boss_04_c …
```

顺带修了 `_read_player_pool()` 写死 `rng.seed = 20261102` 的问题（注释说"走对局种子"
但其实是每局同一手，而且联机两端要能由同一串命令复现）。洗牌用本地 Fisher–Yates，
**不能用 `Array.shuffle()`** —— 它走引擎全局随机、不吃种子。

### 血条：棋子本体已经对了，漏的是**没有队伍号的那一层**

12 只棋子的血条这次实测全是队伍色（含之前出错的四只核心）。
截图里那条不对的，是棋子自己 `get_parent().add_child(...)` 出来的单位 ——
它没有 `team_id`，`_tint_head_hp_bar()` 直接早退，于是血条退回场景默认红，
**自家召唤物看着像敌方**。

**修法只动显示，不动阵营**：`BossBase` 新增 `display_team`（-1 = 跟随 `team_id`），
上色函数读它；对局场景给每只棋子一个 `PieceHost`，
`child_entered_tree` 时把 host 的队伍号借给没有队伍号的 BossBase 子节点。
**故意不写 `team_id`** —— 那会连带让召唤物开始索敌、也开始挨打，
属于逐招裁剪表要定的事，不该塞进一个显示修复里。
附带好处：特效/飘字/落地的巨剑现在都落在各自 host 里，
`Pieces` 不再堆垃圾，host 空了自动回收（否则"棋子数"会把空壳也算上）。

**判据**：`probe_match_entry` 18→21 项，新增三条 ——
AI 池与玩家池的重叠数不得超过"卡池装不下"的下限（本存档 = 0）；
往 host 里塞一个没有队伍号的 BossBase，血条必须借到主人的颜色；
且它的 `team_id` 必须仍然是 -1（证明没越界改阵营）。

## 6j. "一到选牌就时间暂停"：停的不是引擎，是镜像（2026-11-03 用户报）

### 先量，别猜

直觉是"选牌窗口时停 → 引擎被停了"。实测**不成立**：
`tools/diag_match_pause.tscn` 每 0.5 秒打一行，整个选牌窗口里
`Engine.time_scale=1.000`、`GameState.time_flow_base=1.000`，
棋子也在动（105px / 164px 每采样），血量也在掉（13716 → 9486）。
**引擎根本没停。**

### 真正停的是"真棋子 → 规则层"的那一层镜像

`_tick_battle()` 长这样：

```gdscript
if _fighting:
    combat.step(cards, delta * time_scale())   # ← 只有这里镜像
    ...
    return
# 时停的选牌窗口
timer -= delta                                  # ← 一帧都不碰 combat
```

`MatchLiveCombat.step()` 是唯一把真棋子的 `current_hp` / 死亡读回 `cards` 的地方。
它不在选牌窗口里跑，于是那 10 秒内：棋盘上已经躺了一只，
`cards[i]["alive"]` 还是 true、`hp` 还是满的 ——
HUD 的「我方存活 X／对方存活 Y」和画面直接对不上，玩家读成"时间暂停了"。

### 修法：把"结算伤害"和"镜像状态"拆成两个方法

`MatchCombat` 新增 `sync(cards)`（抽象模型空实现），`MatchLiveCombat` 的读回逻辑挪进去、
`step()` 调它；`_tick_battle()` 在**分支之前**先 `combat.sync(cards)`。
这样两边语义各得其所：抽象模型的"选牌时停"照旧（不结算伤害，千局模拟结果不变），
真棋子模型的镜像每帧都走（棋盘上发生什么，规则层当场知道）。

**判据**：`probe_match_pieces._check_sync_in_pick_window()` —— 放两只真棋子进场、
把 `_fighting` 拨回 false、`timer` 设成满窗口，然后杀掉一只、只 `advance()` 一帧，
断言 `cards[i]["alive"] == false` 且另一只的 `hp` 与真实值一致。
负测：撤掉那行 `combat.sync(cards)` → `alive=true hp=27000`，当场红。

> 这一节解决的是"读数对不上"。用户接着要的是另一半：那段时间**本来就该停住** ——
> 见 6k「时停要做成真的：两层闸门」。

## 6k. 时停要做成真的：两层闸门（2026-11-03 用户选 B 案）

6j 把"看着像时停"的成因修掉了，但用户要的其实是另一半：**那段时间本来就该是停的**，
而且要停得彻底 —— "不仅要冻结 boss 的动作、技能的状态，还有 boss 身上的 buff、debuff"。

### 两层闸门，缺一不可

| 闸门 | 冻住什么 | 为什么单独不够 |
| --- | --- | --- |
| `get_tree().paused`（过程） | 物理积分、`_process` / `_physics_process`、Tween、粒子、动画，以及**全部按 delta 计时**的东西：招式状态机 `state_timer`、冷却、`_tick_debuffs` 的剩余时间与点燃跳伤 | 拦不住 `get_tree().create_timer()` —— 它的 `process_always` 默认 true，树停了回调照样触发。11 个 BOSS 脚本用它排招式落地时刻（赫连霄的雷、火麟的陨、石犼的爪…） |
| `BossBase.world_frozen`（后果） | 延迟回调真正落到棋盘上的三件事：`deal_damage_to()` 掉血、`apply_debuff()` 挂状态、`_show_skill_text()` 飘字幕 | 它只管得住"从 BOSS 基类走的东西"，管不了 Tween / 粒子 / 动画 / 子类自己 `_physics_process` 里在 `super()` 之前做的那段 |

规则层给判据，场景层只执行：`MatchState.time_stopped()` = pick / lock / deploy
全停 + battle 未开打时停（含"己方已提交、还在等对面"的空档）+ final / over 不停
（over 停了会把死亡淡出和结算动画一起冻在半路）。

### process_mode 那条坑（第一版就栽在这）

第一版写的是"对局场景根 `PROCESS_MODE_ALWAYS` + 棋子那支退回 `PAUSABLE`"，
实测**冻不住**：窗口里点燃照跳、延迟伤害照落地。
`tools/diag_pause_topology.tscn` 量出来的可用规则只有一条 ——
**场景根保持 INHERIT 时，只有显式写 ALWAYS 的分支在暂停里照跑**
（暂停 0.4 秒：INHERIT / PAUSABLE 叶子 0 帧，ALWAYS 叶子与 HUD 的 INHERIT 孙子 25 帧）。
于是帧驱动与棋盘点击搬到叶子节点 `MatchDriver`（ALWAYS），HUD 那支 CanvasLayer 写 ALWAYS，
其余整棵对局树跟着 pause 冻住。探针根节点也**不能**写 ALWAYS，否则它作为对局场景的祖先
会把整棵树带进同一条歧路，量出来全是假绿。

### 三条负面测试（证明两道闸门都是承重的）

1. 去掉 `deal_damage_to()` 里的 `world_frozen` 判断 → 窗口里那发 500 点延迟伤害照落，
   `时停里延迟伤害不落地` 与 `回调跑完后棋子仍然一动不动` 当场红 2 项。
2. 去掉 `_tree.paused = v` → `窗口里棋子不再被处理` 与 `离场前先确认是冻着的` 红 3 项
   （说明"过程"这一层不是"后果"那层的重复保险）。
3. 探针自己的两处假绿已修：GDScript 的 lambda **按值捕获局部变量**，回调里给局部变量赋值
   外面永远读不到 → 改成成员变量；`is_physics_processing()` 读的是"开关有没有开"，
   暂停时仍返回 true → 判据换成 `can_process()`。

### 整局与离场

`probe_match_freeze` 第三节把整局加速跑完：闸门一局里开合十几次，
打到 OVER、结算面板真的显示、离场（`_exit_tree` 兜底 + `_return_to_city` 明账）之后
`paused` 与 `world_frozen` 都复位 —— 主城绝不能是在暂停态里加载的。

## 6l. 棋盘数值：虎妖打不出伤害、剑客超设计 2.6 倍（2026-11-03 用户报）

用户口径：**只改棋盘模式的数值，不要影响其它地方的 BOSS**。两条都不是"数值给低了"，
量完发现一条是 bug、一条是校准口径错。

### 虎妖：它的伤害根本不读 `attack_power`

对决实测（量尺=两仪、22 秒）：虎妖打到对面的有效 DPS = **2**，而设计名义是 1062；
同期刀客 1109 / 名义 1080 正常。查下去：虎妖是唯一走通用 `scenes/boss/boss.tscn`
（`prototype_boss.gd`）的棋子，它的伤害是 `MELEE_DAMAGE 15 / PROJECTILE_DAMAGE 12 /
ELEMENTAL_DAMAGE 18 / SMASH_DAMAGE 25` 这几个 @export 常数 × 阶段倍率，
**一次都没读 `attack_power`** —— 于是校准表给它抬到 26579 攻击力完全是空转。
它六成的招是远程弹体（掷石 / 妖丹 / 群砂），一并走这些常数，所以整只几乎不痛不痒。

修法不动那些常数（那会改到秘境 / 塔 / 演武场的虎妖面板），而是只对棋子乘倍率：

- `MatchDB.FLAT_DAMAGE_CARDS = ["boss_huyao"]` + `MatchDB.match_damage_scale(id)`，
  倍率 = `ATTACK_CALIB ÷ UNIT_ATTACK_POWER` = **265.79 倍**（正是当初那次校准想表达的倍数）；
- `BossBase._match_damage_scale()`：**`team_id < 0` 恒返回 1.0**；
- 两个出口都挂上：`deal_damage_to()`（近战 / 踏地）与 `_spawn_projectile()` 里交给弹体的
  `ally_scale`（弹体不走 `deal_damage_to`，漏了它只补到四成输出）。

探针里这一条是对账式的：同一记 `deal_damage_to(100)`，PvE 那侧扣 **100.0**，
棋盘那侧扣 **26579.0**，比值正好是倍率 —— 说明"改了棋盘、没碰 PvE"不是嘴上说的。

### 剑客：一次限制只值 10%，真正的原因是校准低估

按用户建议加了「满层一剑开天·剑意盈天」棋盘一局一次：
`HEAVEN_FULL_CASTS_MATCH = 1` + `_heaven_full_allowed()`（同样只看 `team_id`，PvE 不限），
判定收在 `_heaven_will_be_full()` 一个函数里 —— 强制抢放、评分加分、招名、起手定形态
**四处读同一个判定**，否则会报"盈天"的名字、落普通一剑。
唯一一次记在 `_fire_heaven`（打出去才算），`_abort_heaven` 会退回，弹刀不白烧。

实测这次削弱只把剑客从 2788 降到 2512 DPS（约 10%）—— 因为 22 秒对决里它本来也就放得下一两次。
它"太强"的主因是**校准表低估了它**：`ATTACK_CALIB` 原来是拿"对一只不还手的同类假人打 10 秒"量的，
而剑客的大头在二阶段、天剑阵与万剑成型之后，10 秒窗口把这些整个切掉，
于是校准补了过高的攻击力。实测有效 DPS 2491 = 名义 945 的 **2.64 倍**，
而且先后手两侧读数是 2471 / 2511（差 1.6%）—— 这个测量可信。

### 6m. 卡片要有卡片的感觉（2026-11-04 用户：「现在就像一张图平铺在面前」）

用户口径：**选牌时像在卡包里挑，落到棋盘上也要是一张牌**。之前两处都只是一张裸图 ——
手牌是 `TextureRect` 贴原画 + 牌**外**一行 Label，棋盘是 `Sprite2D` 贴原画 + 一块队伍色矩形。
没有框、没有圆角、没有厚度，所以读起来是"图"不是"卡"。

做法是**不自造第二套卡片语言**，直接接卡包那套：

| 位置 | 现在 | 以前 |
|---|---|---|
| 选牌 / 锁定 / 布阵 / 出手 / 结算 | `CardFace`（与卡包封面同一支渲染器：圆角 + 双层金框 + 四角金线 + 华彩流彩），名字与角标**画在牌里** | 裸 TextureRect + 牌外 Label |
| 棋盘上的棋子卡 | `MatchCardToken` 一次 `_draw()` 叠五层：投影 → 卡套（队伍色描边）→ 圆角卡面 → 金框+四角金线 → 名牌 | Sprite2D + Polygon2D 色块 |
| 牌背 | 运行时烘一张 128×192：圆角 + 金框 + 菱格织纹，**全局唯一一张** | 64×96 纯色块加一圈 2px 边 |

`scripts/match/match_card.gd`（`class_name MatchCard`）是两边共用的唯一出口：
`cover_style()` 取卡包封面同一张变体、`accent()` 取同一个配色、`corner_radius()` 与
`CardFace._sync_geometry` 同口径（短边 4.5%，夹 6–20px）。
所以「我在卡包里挑的就是场上那张牌」是看得出来的，不会再出现选时一个样、上场另一个样。

四条踩出来的坑：

1. **圆角不能靠着色器**。棋盘卡是一个 Node2D 一次 `_draw()` 画完五层，而
   `draw_texture_rect()` 没有逐次绘制的材质入口 → 圆角必须预先烘进贴图 alpha
   （`MatchCard.rounded_art()`，每位烘一张 256×384，整局共用）。
2. **圆角环每个角只许扫 1/4 圈**。第一版写成整圈，四个角各绕 360° → 多边形自交 →
   `draw_colored_polygon` 报 `Invalid polygon data, triangulation failed`，投影和卡套整个不画。
   包围盒查不出来（照样是 120×180），**只有面积查得出来**：探针加了一条鞋带公式
   断言面积 = `w*h − (4−π)r²`。
3. **这版 Godot 的 `Font` 没有 `get_string_width()`**（Godot 3 的名字），只有
   `get_string_size(text, alignment, width, font_size)`，而且第 2 参要 `HorizontalAlignment`
   不是 `TextServer.Direction`。写错不报编译错，是每帧刷 `Nonexistent function` 且 `_draw` 后半段静默不执行。
4. **角标底板不能是半透明 accent**。`UIKit.chip` 的底是 accent 14% 透明，压在亮卡面
   （火麟 / 气君 / 剑客）上文字直接化掉。改成不透明暗底 + accent 描边，宽度按字数收
   （布阵的「正 / 反」只有一个字，撑成 44% 卡宽像一条横幅）。

顺带修掉一条被卡片暴露出来的老碰撞：右侧手牌面板顶边原本从 `GUTTER=10` 起，
第一张牌的右上角正好压在设置按钮（84×32 @ y=6，底边 38）下面。以前那个角落是空的所以没人看见，
有了「已选 N」角标之后挡掉的就是操作回执 → 面板顶边抬到 `HAND_TOP_CLEAR = 44`。

**反面依旧不许泄露身份**：`MatchCardToken` 的名牌整块只在正面画，牌背全局同一张贴图；
探针跑完整局断言 6 张暗牌从头到尾 `_face_front == false`。
棋子出生时暗牌才翻面（`scale.x` 压到 0 再展开，中途换面），然后整张牌压暗成"已出"记号。

**回归**：新增 `tools/probe_match_cards.tscn` **27 项**（圆角环闭合与面积、圆角口径三档、
牌背全局唯一且 2:3 且四角透明、卡池 16 位全部 `CardFace.configure()` 成功、
卡面四角真透明而中心不透明、反面不翻面、卡套装得进格子、真跑一局 41 张手牌 0 张退回裸图、
12 张 token 里 6 张暗牌 0 泄露）。
对局侧 249/0（cards 27 + rules 51 + pieces 32 + faction 27 + entry 21 + ranged 10 + freeze 42 + balance 39）、
clicks 25/0（窗口化）、卡包侧 holo_pack 41/0 + ink_cards 281/0、PvE 侧 91/0。

### 6n. 卡面可选 + 悬停视差（2026-11-04 用户第二轮反馈）

用户两条：① 「为什么不能选择卡包里的卡面（无背景 / 水墨 / 原画），只能默认有背景炫彩 ——
这里应该默认是自己卡包里展示的那一张」；② 「鼠标移动时卡面没有动态效果」。

**① 卡面种类**：`MatchCard.cover_style()` 原来写死取 `card_variants[0]`，
而收藏册的封面是 `CodexDB.ordered_variants(entry)[0]` —— **玩家在卡包里拖出来的卡序**
（`CharacterData.card_order`，achievement_view 拖卡序时写入）。两个"第一位"不是同一个东西，
所以他把水墨拖到封面、进对局看到的还是华彩。改成：

- 默认档 `""` = **跟随卡包**，直接取 `ordered_variants[0]`，与收藏册同源；
- 操作条上加一个循环按钮「卡面：跟随卡包 / 原画 / 华彩·有背景 / 华彩·无背景 / 水墨」，
  存在 `CharacterData.match_card_kind`（进存档，旧档没有 → `""`）；
- **该档没解锁就回退到封面**（对手池里的卡也必须画得出来，不能因为没解锁就空）；
- 换档要 `MatchCard.clear_cache()`：两张缓存分别按 `boss_id|档位` 和**贴图路径**记，
  按 boss_id 记贴图就会切档后一直端出旧图。
- 按钮放在操作条而不是每张牌上：布阵与选牌靠的就是点牌，牌上再挂按钮一定误触。

**② 悬停视差**：上一版为了保住按钮点击，把 CardFace 整棵子树设成 IGNORE，
结果鼠标事件根本到不了华彩卡 —— 视差整个没有。

第一版修法（`hover_only` 输入模式 + 子树留 PASS）**是错的**，而且被结构探针放过了：
`MOUSE_FILTER_PASS` 并不会把按下/松开传回父按钮，实测牌直接点不动。
真正的通路是**由按钮转发**：卡面子树保持全 IGNORE（点击路径一点没动），
按钮 `gui_input` 把 motion 转给 `CardFace.set_hover_point()` → `HoloCardView.set_hover_point()`。
这样视差跟手、tooltip 仍在按钮上、触屏拖拽也走同一条。

### 6o. 两条被这轮踩实的引擎事实

1. **本机 MouseFilter 枚举是 `STOP=0 / PASS=1 / IGNORE=2`**，与 Godot 文档的
   `STOP / IGNORE / PASS` 顺序不同。日志里写数字必被骗（我把 `filter=1` 读成 IGNORE，
   差点得出"华彩卡收不到事件"的错误结论）。判据一律用 `MOUSE_FILTER_*` 常量，
   诊断里把三个常量的值一起打出来。
2. **合成点击要在 motion 与 press 之间过一帧**。同一帧里 push motion+press+release，
   按钮的 `under_mouse` 还没建立，按下会被当"从别处抢到的按下"丢掉 ——
   表现为"同一个坐标点两次，只有第二次中"，看着像游戏有 bug，其实是测试工具不稳。
   另外 `_toggle_pick` 是**切换**，点两下应该 1→0，判据要按这个写。

**为什么必须有 `tools/shot_match_hover.tscn`**：结构探针只能证明标志位，证明不了画面在动。
它把鼠标移到卡面左缘拍一张、右缘拍一张，直接量像素差，并且**读 `HoloCardView._target_view`**
—— 那个值只有 motion 真的抵达卡面才会被写，不会被 idle motion 的回弹尾巴骗过去
（第一版就是只量像素差，拿到了 MAD 20 的假绿）。

**回归**：`probe_match_cards` 40/0（新增：默认档 == 收藏册封面逐位对账、五档都能切出来、
未解锁档回退仍有牌面、换档取到另一张图、卡面子树全 IGNORE、每张按钮都接了 motion 转发）、
`shot_match_hover` **9/0**（事件抵达 + 横向 MAD 13/255、93.6% 像素变化 + 点一下选中再点取消 +
切档画面真的变）、clicks 25/0、rules 51 / pieces 32 / faction 27 / entry 21 / ranged 10 /
freeze 42 / balance 39、卡包 ink_cards 281/0 + holo_pack 41/0 + card_assets 16/16 位 64 张、
PvE 91/0。截图 `output/match_ui_*.png`、`output/hover_{left,right}.png`。

### 6p. 阶段读数与可点状态重排（2026-11-04 用户第三轮反馈）

用户两条：① 「现在到哪一阶段和倒计时都在左上角，一堆文字堆在那，很难一下锁定有效信息」；
② 「激活阶段一眼辨不认可选哪些牌 —— 可选牌边缘要有淡淡的动态呼吸灯；敌我全靠红绿边框，
要更好分辨，例如选自己牌时敌方牌被灰色笼罩」。

**① 布局：棋盘让出两条带，文字不再压在卡面上。**
根因不是字号也不是颜色，是 `_fit_camera` 以前按整个 `vs.y` 算缩放，棋盘正好铺满上下，
HUD 只能叠在棋盘与卡面上 —— 那当然读不出来。现在：

```
const TOP_BAND := 96.0        ## 顶部读数带
const BOTTOM_BAND := 84.0     ## 底部操作带
const BOARD_OVERHANG := 30.0  ## 棋盘上下各再让一条（见下）
usable_y = vs.y - TOP_BAND - BOTTOM_BAND - BOARD_OVERHANG * 2.0   # z 按这条可用带算
```

`BOARD_OVERHANG` 是截图验收补上的：归属签从牌顶探出 13px、呼吸灯外圈比牌再大 13px，
都**在牌的包围盒之外**。只让两条带时棋盘正好顶到带子下沿，1280×720 实机截图里
最上一行的牌被切掉一截、棋子被顶带啃了一口。留出这条之后棋盘从 540 缩到 480，
手牌面板反而宽了（708→768，卡面 166×250 → 181×272）。

| 内容 | 新位置 | 样式 |
|---|---|---|
| 倒计时 | 顶带**正中间** | 30 号字，暖金；**最后 5 秒转红** |
| 阶段提示（该干什么） | 顶带居中第二行 | 17 号，暖金，通宽居中 |
| 存活 | 顶带左侧小字 | 次要读数，不与倒计时抢位 |
| 注额 / 可选 | 顶带右侧小字 | 同上 |
| 操作回执 | **底带**居中 | 金色 + 描影 |
| 五个按钮 | 底带居中一排 | — |

顶带那一行用**锚点分三栏**（CENTER_LEFT / CENTER / CENTER_RIGHT），不用 Container ——
HBox 会把居中的倒计时挤成左对齐，"正中间上方"就没了。
手牌面板的上下边界也跟着夹进两条带之间（`TOP_BAND+6 ~ vs.y-BOTTOM_BAND-4`），
所以第一张牌不会再钻到倒计时底下。

阶段文案同时收紧：一行只回答"现在该干什么"，数字一律挪到两侧与中间计时里。

**② 可点状态：三条通道各管一件事，互不混用。**

| 通道 | 编码 | 为什么用它 |
|---|---|---|
| 归属 | 队伍色卡套边 + 牌顶**归属签形状**（己方朝上梯形 / 对方朝下倒钩） | 只靠红绿，色弱玩家和余光扫视都分不清；形状差是瞬间可读的 |
| 可点 | 卡套外一圈**香槟白**呼吸灯：常亮底圈 alpha 0.40 + 呼吸圈 0.30→0.92 | 与手牌那圈呼吸边同一套语言；底圈保证任何时候扫一眼都认得出（见下两条补正） |
| 不可点 | 整张压灰：贴图 modulate (0.58,0.59,0.63) + 灰纱 alpha 0.38 | 就是用户要的"敌方牌被灰色笼罩"，但要留得住"这是谁" |

两处补正是**在真实显示尺度上看截图**才发现的（棋盘 zoom≈0.31，一切 1:1 尺度的设计都要重看一遍）：

1. 灯色原来用 (1.0,0.84,0.42) 的金 —— 落到屏幕上与己方套边的**青绿几乎分不开**，
   "能点"和"是我的"糊成同一件事。改成偏白的香槟金 (1.0,0.95,0.78)，读作"光"而不是"颜色"；
   `MatchCellHint` 的空格框也换成同一色相，全场"现在可以点这里"只用一种光色。
2. 只靠呼吸的话，最低相位 alpha 0.30 时四张可点牌在截图里只看得见一张，
   其余三张和点不了的牌混在一起 —— 玩家是逐帧扫视的，不能靠"刚好撞上亮的相位"。
   于是加了一圈**不参与呼吸的常亮底圈**。
3. 压灰原来 modulate 0.46 + 灰纱 0.46，实机变成一块黑牌，玩家下一步该防谁全看不出来；
   抬到 0.58 / 0.38。
4. 空格提示的线宽 2 世界 px 在 zoom 0.31 下只剩 0.6 屏幕 px —— 截图里整片格子
   只有中心一个点、呼吸框等于没画。改成 6.5 世界 px（≈2 屏幕 px）、菱形 9→14，
   alpha 区间 0.16–0.52 → 0.30–0.74。

倒计时那一格还补了一条：不等待玩家的阶段（对方布阵）原来显示一个**冻住的数字**，
看着像卡住或像超时，现在写 "—"；顶带右侧"注额…可选 N"原来右边界只让开 `GUTTER`，
后半截整个钻到右上角「设置」按钮底下（settings_ui 占 `vs.x-90 … vs.x-6`，
与战斗 HUD 的 TimeLabel 同一套 -104 契约）。

⚠ 可点集合**一律问规则层** `legal_activate(PLAYER_TEAM)`，不按队伍猜 ——

### 6q. 「我输了但还有一张牌没翻出来」—— 代选循环多走一格（2026-11-04 用户实机截图）

截图证据：结算页写 `结束方式：clear_field`、`我方存活 0／对方存活 4`，
棋盘上有一张己方牌**还是牌背**。放大看那块牌：斜织纹牌背 + 队伍色套边，
而且**名牌整块没画** —— 名牌的条件是 `_face_front`，所以它不是"翻面动画没播完"，
是**从头到尾没被翻开过**。

规则层的千局模拟一直断言 `activated == 12`，为什么实机漏了一张？
因为模拟是**两边同一帧一起提交**，而实机的节奏是一先一后：

```
AI 侧 0.4 秒就提交（_ai_tick）→ pending = [-1, c1]
玩家想满 10 秒 → 窗口到点，规则层替他代选
for team in 2:
    team=0：decide → _cmd_activate(0, c0) → 双方凑齐 → 当场结算本轮
            （round_index += 1、pending 清空、开打）
    team=1：循环不知道本轮已经结算完了，照旧往下走
            → 把牌塞进**新一轮**，留下 pending = [-1, c?]
下面那条"只有一方有合法手"的分支一看 pending 有值 → 把**新一轮**也单方面结算掉
```

于是六轮里有一轮只激活一张，12 张只翻出 11 张；轮次跑满 6 就进终局，
剩那张牌既没翻面也没上场，玩家**少一个人打完了整局**。
`_check_timeout_path()` 抓不到它，是因为那条测的是"两边都走代选"——
那种顺序下结算恰好落在循环的最后一格，循环也就跟着结束了。

**两道守卫，各钉一件事**（`match_state.gd`）：

| 守卫 | 钉住什么 | 拆掉后哪条判据转红 |
|---|---|---|
| 代选循环里 `round_index != round_before → break`（循环后同一条件直接 return） | 一轮只结算一次，不把牌塞进新一轮 | 「翻完 12 张恰好只用 6 轮」→ **最多 9 轮** |
| 进终局要 `round_index >= 6` **且** `_all_flipped()` | 没翻完绝不判负（轮次跑在牌前面就再开窗口） | 「没有一张牌扣着牌背」→ **漏 200 局 / 最少只激活 9 张** |

新增 `_check_half_submit()`（400 局「一方先提交 + 另一方超时代选」，两种先后都跑）
与诊断工具 `tools/diag_match_unflip.tscn`（真跑整局、逐帧比对 `activated` 位，
把"规则层没激活"和"激活了但场上还是牌背"分成两类计数）。
回归：rules **55/0** · pieces 32/0 · faction 27/0 · entry 21/0 · ranged 10/0 ·
freeze 42/0 · balance 39/0 · cards 50/0 · 诊断 20/20 局 12/12 全翻。
负面测试实测过：只拆循环守卫红 1 项；两道都拆红 3 项。

### 6s. 布阵可以拖牌上场，手里那张半透明跟着鼠标（2026-11-04 用户提）

交互：在布阵手牌上**按住 → 拖 → 在发亮的空格上松手**就落子。
原来的「点选→点格」保留不动，两条路共用同一份 `_sel_card` 与同一套空格提示。

| 环节 | 做法 |
|---|---|
| 阈值 | 按下后走够 `DRAG_START_PX = 14px` 才算拖；走不够就是原来的点选（`pressed` 照常发） |
| 手里那张 | `_make_card_ghost()`：与手牌同一套 `CardFace`（框 / 圆角 / 名牌），`modulate.a = 0.55`，中心对准光标，按横向位移做 ±7° 倾斜 |
| 源牌 | 压暗到 `a = 0.42` —— "这张被我拿起来了" |
| 目标格 | `MatchCellHint.set_hover(cell)`：那一圈加粗 +5px、提亮 +0.26 alpha、菱形 +7px |
| 能不能落 | 落在合法空格 → 手里的牌是白的；落在棋盘外/已占格 → 发灰压暗（松手前就知道结果） |
| 回执 | 开始拖「拖到发亮的空格松手」/ 落子「已落到第 N 行第 M 列」/ 取消「松在棋盘外，取消落子（牌已选中…）」 |

**四个必须写住的实现细节：**

1. **ghost 的子树全 `MOUSE_FILTER_IGNORE`**，而且它挂在 HUD 根的最后面。
   它若吃输入，自己的松开事件就回不到按钮上，牌会永远黏在光标上。
2. **靠按钮捕获鼠标这件事**：Control 在按下后会持续收到移动与松开，
   所以松开落在棋盘上时 `_on_hand_drag` 照样触发，而 `pressed` 不会发（松手点不在按钮内）——
   「拖到棋盘=落子」与「点一下=选中」天然不打架，不需要吞事件。
3. **合法性一律现问规则层**（`_drop_ok` 走 `free_cells`/`occupied_cells`），
   不读 `MatchCellHint.cells` 那份缓存：提示是按签名延后一帧重算的，
   拖动的头一帧可能还是空的，照它判就会闪一下"松手也落不了"的灰牌。
4. **拖动期间把阶段计时按住**（`tick()` 里 `_stage_timer = maxf(_stage_timer, 1.0)`），
   否则玩家拖到第 10 秒被「到点代选」抢先布掉，松手落空。

**顺带修掉一个既有缺陷**：布阵手牌原来只在**玩家下一次点牌**时才重建，
于是①拖完一张后那张还留在手上，②AI 落完轮到玩家时没人重建 → 面对一张空手牌。
现在每次 `deploy` 事件都重铺（`_refresh_hand_if_idle()`），
但**正在拖的时候跳过**——重建会 `queue_free` 掉按钮，而拖拽的事件链正挂在那个按钮上，
按钮一没，移动/松开全丢，屏幕上留一张永远跟不掉的半透明牌；松手时 `_end_drag` 自己补一次。

## 6t. 点「开战」卡一下：645ms 是从哪来的（2026-11-05 用户实机报）

用户原话：「快速模式点击开战时，一次激活 12 个 boss，会有很明显的卡顿，你想一想怎么优化一下」。
拍定三件一起做：**线程预载 + 入场摊帧 + 削掉每实例的重复构建**。

### 先排除，再定位（每一刀都是量出来的，不是猜的）

| 试过的假设 | 量法 | 结论 |
|---|---|---|
| 12 只同时进树太重 | `measure_quick_spawn_cost`：同帧 572.8ms + 首帧 73.1ms = **645.8ms**（预算 16.7ms 的 38.7 倍）；改成 2 只/帧后峰值 231ms | 卡顿确实在进树，但"多"不是原因 |
| 纹理首次上传 / 着色器编译 | `measure_prewarm_feasible`：`visible=false` 照样 421ms | 不是 GPU 侧，是主线程在算 |
| `BossRig.setup()` | 直接调 setup 只有 15.8 / 29.2 / 11.7ms | 不是骨骼构建 |
| 一次性成本 | `measure_piece_ready_cost`：石犼 **每**次实例 420–485ms | 不是一次性的，是每场都要重付 |
| ⇒ 拆进 `_build_rig` | 临时插桩逐项计时 | **`load(sprite_frames)` 一句 455ms（石犼）/ 190ms（刀客）**，`attach` 只 0.1ms |

根因写在 `scripts/visual/skin_warm.gd` 抬头：这些招式序列帧表是
`compress/mode=1` + `vram_texture=false`（**有损压缩、非 VRAM**）的导入档，
`load()` 要在主线程把整张图集解成 RGBA8 —— 两张表实测吃掉 **270MB 显存**，
解码自然是几百毫秒。而 Godot 的资源缓存**没人引用就连带纹理一起丢**，
所以"上一场读过"不省钱：场上实例全灭 ⇒ 下一场从解码重新开始。

### 修法（三层，缺一层就还是卡）

1. **`SkinWarm`（`scripts/visual/skin_warm.gd`，新增）**：`load_threaded_request` 把工作挪到
   加载线程，实测两张表同时预载墙钟 438ms 而**主线程峰值帧仍是 16.70ms**（基线 16.67）。
   到位后把 Resource **押在类里**，同场第二次实例从 173/197ms 掉到 43/36ms。
   ⚠ 只有被 `request()` 点名的路径才押 —— 大世界 / 塔 / 演武场一行没改、行为不变，
   显存峰值也不会超过"这一局本来就要摆的 12 张牌"。
2. **谁点名**：`_drain()` 的 `deploy` 分支 = "这只一定会上场"的最早信号 ⇒
   `MatchAdapter.warm_boss()`。它只解析**路径**，路径到手后 `SkinWarm` 扫场景里
   `SkinVisual.visual_id` 自己把 rig / 招式表接上 —— 不另立"BOSS→贴图"对照表（那张表一定会漂）。
   两个真坑因此暴露并被探针抓到：① 核心首领的皮是**运行时**从区域配置覆写的
   （`world_enemy.gd:136`），只扫场景会预载错那一份 —— 石犼场景写 `world_core_shihou`、
   真上场穿 `boss_huyao` 那张 455ms 的大图；② 古猿那类核心**没有专属场景**，
   装配兜底到通用 `world_enemy.tscn`，路径解析必须返回"真正会被实例化的那一条"。
3. **入场摊帧 + 计时对齐**：`_flush_spawn_queue()` 按**时间预算**（一帧只花 8ms 在落场上）
   而不是按只数，因为单只成本 35–150ms 随机型与首战浮动，写死 2 只/帧在慢机器上照样
   一帧 150ms。落场的同时 `_spawn_hold` 把终局计时闸住（`tick` 里 `advance()` 排在
   `drain()` **前面**，所以闸必须在点「开战」那一刻先落下，晚一帧就多算一帧 ——
   探针实测到 0.1457s 的漏量）。规则层没动：**12 只仍然是同一刻同时激活**。

### 三条必须写下来的反面结论

- **预载反而更糟的那个版本**：让落场不等预载，`SkinWarm.resource()` 撞上在途请求会
  **同步等待**，实测「摆完立刻开战」那一帧涨到 **1609.9ms** —— 比优化前还差。
  所以 `_flush_spawn_queue()` 必须先看 `SkinWarm.is_busy()`，等一手工作线程（上限 120 帧兜底）。
- **交错落场**：`quick_start_battle()` 的事件流是"对方 6 只在前"，直接排队 = 送对面半秒先手。
  入队前按队伍 `_interleaved()`，实测落场序列 `[1,2,3,4,6,7,8,10,12]`、前两只一边一只。
- **离场必须放开引用**：一张表 100–200MB 显存，押着不放会把显存吃穿。
  `_exit_tree` 里 `SkinWarm.clear()`，下一场重新解码 —— 但那是在工作线程，点开战不卡主线程。

### 前后对照（`tools/measure_open_fight_cost.tscn`，窗口化同进程两遍）

| | 最坏一帧 | 前 4 帧合计 | 12 只落齐 |

| 优化后 · 摆完立刻点（预载还在路上） | **16.7 ms**（一帧没卡，等线程解码） | 45.7 ms | 稍后 |

剩下的每只 35–90ms 是**真活**（`BossRig.setup` 约 20ms + 血条/碰撞镜像/子类 `_setup`），
不是重复构建；再往下就是改 rig 构建本身或改贴图导入档（`compress/mode=2` VRAM 压缩可把
两张表从 270MB 降到约 1/8，但那是全项目 77 张贴图的画质与重导决策，归美术定稿，未擅动）。

| 每行读数 | 招式名 + 数字 + **占比横条**（`UIKit.mini_progress`），不写百分号、不加次数列 | 次数/均伤是纯派生数，四列并排就成 Excel，撞"避免方框堆叠"那条 |

### 实现上真正省事的两个决定

1. **招名不另立表**：`show_skill_name_at_windup` / `show_skill_line` 这两条**招名字幕入口**
   传进去的字符串已经是玩家可读的招式名（`_form_name_of(skill_id)`、`MoveDB` 的 `form_name`、
   `SkillDB.get_skill_name`）。在这两处盖一个"当前招式"戳 ⇒ 一处覆盖全部 16 张卡池，
   包括只走通用 `AttackKind` 路径的核心首领（`WorldEnemy._attack_kind_skill_name`）。
2. **卫星归属在棋局层统一盖戳**：`_stamp_report_owner()` 挂在已有的 host
   `child_entered_tree` 上，凡是 host 子树里不是棋子本体的节点都指回那只棋子。
   这样既不用去 8 个卫星脚本各补两个字段，也**绕开了并行会话正在改的
   `fold_field.gd` / `domain_boss_04_c.gd`**（叠纸的场地照样能归对人，只是行名暂时走主人当前戳记）。

### 探针抓到的三条真坑（都不是"看代码能看出来"的）

- **`String(null)` 直接崩整局（用户实机抓到，第二轮）**：读来源身上的战报字段时用了
  `String(_report_field(src, "_report_form_name"))`。观澜的镜像 `MirrorImage` **不是 BossBase**，
  压根没有这个私有属性 ⇒ `get()` 回 null，而本机 4.7.2 的 `String(null)` 是
  「Invalid call. Nonexistent 'String' constructor」，函数当场中止。
  修法是加类型收口 `_report_str()`（不是 String 就当空串）。
  ⚠ 探针第一版抓不到它：我只造了"完全无关的裸 Node2D"，那种来源在归属那一步就早退了，
  永远走不到崩溃行 —— 必须造**有主人但没有那两个字段**的来源（`probe_match_report` ④ 第二条）。
- **持续伤害根本不进台账**：`_apply_dot()` 是真伤，绕开 `take_damage`（不触发顿帧与仇恨），
  所以台账必须在 `_apply_dot` 里单独接一笔，行名用 `DebuffDB` 的中文名（点燃 / 阴蚀）。
  为此 `apply_debuff()` 加了第三个可选参数 `from_unit`（只给归属用，不传行为不变）；
  ⚠ `domain_boss_03.gd` 覆写了 `apply_debuff`，签名不同步会**整个子类脚本解析错误**。
- **"出生快照"会把账读成 0**：`_report[card]["rows"]` 在落场时被初始化成空字典，
  只有**离场那一刻**才回写。探针第一版直接翻这个字典，量到"队1 台账 0 / 掉血 3191"。
  判据改成读 `_report_sides()`（它会把还在场的棋子现抄一次）—— 顺带让这条判据
  量的就是**玩家看到的那一屏**。
- **自洽判据不能跨死亡**：一刀 3000 砍在 500 血上，台账 +3000、血只掉 500（过量伤害）。
  所以严格等号只在"还没有人死"的那一帧成立；终局只要求**台账 ≥ 掉血**（少记才是漏路径）。
  另外规则层的 `card["hp"]` 是**延迟镜像**的，第一帧可能台账已有 896 而血还是满的 ——
  采样必须等两边都 > 0。

### 验收

## 6v. 战报第二轮：承伤明细「谁用哪招打了我多少」（2026-11-06 用户追加）

用户第一句话只覆盖了半边，第二轮补上：「对局结束后可以详细查看双方各boss的**受到**哪些boss的技能伤害」。
第三轮按用户选中的那句两问一次做到：承受**按来源棋子分组**，组头是来源名与该来源合计，
组里只列招式名 —— 列不再被长串撑宽（①），层级也清楚（②），
而且不用把「来源 · 招式」这种复合字符串再拆回去（招式名里本来就带「·」，拆错一次错一整列）。

数据结构因此是**两层**：`report_taken = { 来源棋子名: { 招式行: 金额 } }`，
`_taken_groups()` 按"谁打我打得最多"降序发组。

### 结构上几乎免费
受击那一侧本来就在同一个落点算好了减免后的钱、也认得出来源棋子，所以只是在
`_register_damage_report()` 里**同一笔钱多记一份在挨打的那只身上**（`report_taken`），
闸门与输出侧完全相同（`team_id >= 0` 才记 ⇒ PvE 依旧一字不写）。
快照多抄一个字典、`_report_sides()` 多带一组 `taken`、展开后分「打出」「承受」两组。

### 换来的两条更硬的判据
- **逐只**：这只的承受总额 == 它自己掉的血（只在"还没有人死"的窗口里比 —— 过量伤害会把等号打歪）。
  输出侧只能对总量，这条能抓到"记错人"。
- 全局：承受总额 == 打出总额（少抄一侧就红，正是快照最容易漏的那种错）。

键用 **card 下标**而不是名字：棋局允许双方带同一只（见「同场共存」），按名字对键会自己串台。

**验收**：`probe_match_report` 16/0 → **19/0**（+承受分组、+两侧同额、+PvE 两侧都留白）；
`probe_match_report_live` 17/0 → **19/0**（+逐只承受==掉血、+两侧总额相等）；
截图 `output/match_report_view.png`：镇墟石犼展开为「打出 震地 4,187」+
「承受　云隐苍角 6,636」组头 + 组内「角撞·裂岩 6,636」。

## 6w. 战报第三轮：用户实机「我方为什么没有显示」——两个真漏（2026-11-06）

截图里我方六只全是 0 且**点不开**。用 `tools/measure_report_sides.tscn` 真打一局把两侧总额
摆出来，发现不是显示问题，是**账真的丢了一半**，而且丢了两次不同的东西：

| 漏 | 症状 | 根因 | 修法 |
|---|---|---|---|
| ① 整只棋子的账没了 | 三张非核心卡 rows/taken 全空，另一侧却记着挨了它们的打 | 收账挂在 host 的 `child_exiting_tree` 上，而 `BossBase._play_death_animation()` 只渐隐**不 free 节点**，节点后来被谁释放不一定经过这个信号（实测核心卡触发了、非核心卡没触发） | 改挂 **`died` 信号**：血量归零那一刻发，此刻账一定齐；离场信号留作兜底 |
| ② 两侧总额对不平 | 对方打出 198,690 vs 我方承受 164,900 | 观澜死后**镜像还在打**：镜像自己也是 BossBase 且带队伍号，它的打出与承受都记在它身上，而它不是 12 张卡之一，快照收不到 | 承受侧写进 `report_owner`（主人）；快照改成**按 host 子树合并**，逐单位**增量**入账（`meta("report_bank")` 记已入过多少，只补差额，避免重复计钱） |

顺带修掉一个把承受全打成 0 的低级错：`into.get(src, {}) is Dictionary` 判完不插入，
下一行 `into[src]` 直接越界，运行时错误把整个函数吞掉 —— 于是"承受"一列静默全空。
**判据要能红**这条又一次生效：正是「承受总额 == 打出总额」把它逮住的。

### 视图也跟着改
一行原来只报打出，被秒掉的那一侧整列是 0，玩家自然读成"没显示"。
现在一行是 `名字　打出　/　承 承受`，条子仍按打出（与排名同尺度）；
**只要挨过打就能点开**（不再要求打出 > 0），未上场才禁用。

**验收**：`probe_match_report_live` 19/0 → **23/0**，新增四条打完再算的总账判据
（我方打出==对方承受、对方打出==我方承受、没有哪只上场的棋子整本账是空的、真打到分胜负）。
这组只在**自然打到 OVER** 之后才成立 —— 之前那版探针是强制结算的，正好放过这类"死过人才露馅"的洞。
全量回归 **36 探针 / 863 项 / 0 红**。
