# 位面守关者按 `boss_ids` 的数组顺序逐个挑战

万界秘境里每个位面三名守关者，此前**三张卡同时可点**：进了位面就能直接挑最后那只打。
用户 2026-11-12 定：「只能一个一个挑战，不能随意在三个 boss 中选择，例如凡界只能先通关虎妖，
再打刀客，最后打剑客。」

`WorldDB.DOMAINS[].boss_ids` 本来就是有序数组（凡界 = `boss_huyao, boss_01, boss_01_c`），
而且塔层表已由它按「位面顺序 → 位面内顺序」自动生成。所以这次**不新增任何顺序字段**，
而是把这个既有顺序升格为设计口径。

用户逐条拍定以下口径，**这些是设计决策，不是实现细节**：

1. **数组顺序 = 挑战顺序**：门槛判据是「本界第一个还没斩的守关者」，不是新配的序号表。
   以后把某个 id 插到数组哪一位，就等于决定玩家第几个见到它（塔层号跟着一起重排）。
2. **已斩过的永远放行再战**：门槛只压住「还没斩的」。这既保住老档跳着打过的人不被
   收回入口，也让「重打前一关练手」不会被顺序反过来卡住。
3. **境界不参与顺序门槛**：境界不足仍可硬闯是既有设计（`is_domain_realm_ok` 只做风险提示），
   按序挑战不与它叠加成双重锁。
4. **整界锁优先于界内顺序**：前置界没通关时，本界连第一位都进不去，回执沿用
   `domain_lock_reason`（「需先通关 凡界」），不说成「需先击败 两仪真人」。
5. **回执点名「当前该打的那一位」，不是「上一位」**：跳着看过来的时候，玩家要知道下一步
   去哪。剑客锁着而虎妖也没斩时，两张卡都写「需先击败 虎妖」。
6. **拦在数据层与入口，UI 只是表现**：`CharacterData.is_boss_challengeable()` 是唯一判据，
   `BattleResolver.start_domain()` 自己再拦一道；卡面置灰与文案不重算规则。

**状态**：accepted（2026-11-12）。

## 后果与红线

- **万界塔自动跟着有序**：塔层解锁条件是「该层对应 BOSS 已击杀」，位面内顺序化后，
  塔层 1→2→3 自然按序开放，不需要另写门槛。
- **破境天髓不会断链**：每档天髓出自该位面**第三位** BOSS（`ItemDB.FIRST_KILL_REWARDS`），
  顺序化后拿它必须先过前两位 —— 这是门槛变长，不是门槛变死，因为界内不存在「打不过就绕不过去」
  的分支。化神那条链（照影界第三位）同理。
- **没有调试跳转**：F2 开发者面板进不了 BOSS 战，所以不必为它开后门。以后若要加「直接跳某只 BOSS」
  的调试入口，必须**显式绕过**顺序门槛（并只在该入口绕），不要去放宽 `is_boss_challengeable`。
- **卡面上「已击杀」的那张没有挑战按钮**（再战走万界塔），这是改动前就有的表现；
  顺序化没有改变它，但底部规则文案已改成先讲「按序现身」再讲通关条件。
